## 1. 목표와 원칙

야생 활동(채굴·벌목·농사·사냥·낚시)으로 돈(원)을 벌고, 서버 상점·플레이어 거래·치장 콘텐츠에 쓰는 구조를 추가한다.

1. 야생 플레이의 재미와 아이템 가치를 해치지 않는다. **희귀품은 직접 구하는 것보다 비싸게, 주간 한도 안에서만 판다**(v0.8, 13장). 네더라이트·겉날개·토템 같은 최상위 보상은 여전히 돈으로 못 산다.
2. 검증된 외부 플러그인을 쓰고, 서버만의 차별점만 직접 만든다.
3. 화폐는 하나(원). 잔액은 자체 `Bank` 플러그인이 관리하고, 모든 플러그인은 VaultUnlocked를 통해 같은 잔액을 본다.
4. 경제 활동은 선택. 안 해도 야생 플레이에 손해가 없다.
5. **돈이 생기는 곳(공급)은 직업 보상 하나로 시작**하고(v0.8: 직업별 서버 매입을 두 번째 공급원으로 추가, 근거는 14장), 돈이 사라지는 곳(소비)은 상점·치장으로 둔다. 공급원을 늘릴 때는 문서로 근거를 남긴다.
6. 기존 월드·플레이어 데이터와 Travel·Pets·CustomItems를 건드리지 않는다.

### 2.1 화폐는 자체 `Bank` 플러그인으로 (확정)

돈 데이터는 한번 꼬이면 되돌리기 어렵고, 26.3을 명시한 쓸 만한 경제 플러그인이 없다(EssentialsX는 26.1.2, ExcellentEconomy(구 CoinsEngine)는 26.2·NightCore 필요, TheNewEconomy는 유지보수 종료, NexoriaEconomy는 검증 부족). 그래서 처음부터 직접 만든다. 서버 버전을 올릴 때도 우리가 바로 맞출 수 있다.

**`plugins/bank` (플러그인 이름 `Bank`)**

| 항목 | 내용 |
| --- | --- |
| 역할 | VaultUnlocked에 **경제 제공자(Economy provider)** 로 등록. VJobs·EconomyShopGUI·자체 플러그인이 모두 이 잔액을 씀 |
| 연동 | `depend: [Vault]`. VaultUnlocked 2.20.3의 `plugin.yml`은 이름이 `Vault`이고 `VaultUnlocked` 별칭이 없다(2026-11-25 확인). 구 Vault `net.milkbowl.vault.economy.Economy` 인터페이스만 구현(VJobs·EconomyShopGUI가 쓰는 쪽). 첫 연동 테스트(아래 1번)가 통과하면 MVP에 Vault 2 API는 넣지 않는다 |
| 금액 | 잔액은 `long` 정수 원. 표시는 `12,340원`. 소수 처리 규칙은 아래 2.2 |
| 저장 | `plugins/Bank/bank.db` (파일형 SQLite, `journal_mode=WAL`, `synchronous=FULL`). `accounts(uuid, name, balance, updated_at)`, `transactions(id, time_ms, type, from_uuid, to_uuid, amount, from_balance_after, to_balance_after, source, boot_id, context, ref)`, `boots(boot_id, started_ms, last_heartbeat_ms, ended_ms, crash_estimated_ms, status, world_dir, unclean_reason)`, `shutdown_players(boot_id, uuid)`, `meta(key, value)`. `/pay`는 한 줄에 양쪽 잔액이 필요해서 `balance_after`를 `from_`/`to_` 두 칸으로 나눔. `boots`는 기동별 정상·비정상 종료 판정(2.4) |
| 쓰기 방식 | **모든 잔액 변경은 "잔액 검사 → 변경 → 거래 기록"을 한 SQL 트랜잭션으로 처리하고, 커밋이 끝난 뒤에만 성공을 반환한다.** 메모리 캐시는 커밋 후에 갱신하는 조회용 사본. 커밋이 실패하면 Vault에 실패를 반환(상점은 상품을 주지 않음). `/pay`도 출금·입금·로그가 한 트랜잭션. Vault 호출이 다른 스레드에서 와도 되도록 DB 연결 하나를 락으로 보호 |
| 명령 | `/money` (`/bal`, `/돈`): 내 잔액 · `/money <닉>`: 남의 잔액 · `/pay <닉> <금액>` · `/baltop [쪽]` (10명씩, 1분 캐시) |
| 관리자 | `/bank give·take·set <닉> <금액>`, `/bank log <닉> [쪽]`, `/bank refund <거래번호>` (해당 출금을 한 번만 환불, 2.4), `/bank reload` (권한 `bank.admin`, 기본 OP) |
| 송금 규칙 | 최소 10원, **정수만**(소수점 입력 거부), 잔액 초과·자기 자신·음수·0 거부, 오프라인 대상 허용(서버에 한 번이라도 접속한 플레이어만) |
| 로그 | 모든 입출금을 거래마다 1줄씩 `transactions`에 기록. `/bank log`로 조회 |
| 첫 설치 vs 분실 | 2.3 |
| 백업 | `plugins/Bank/`가 `backup.sh` 대상에 이미 포함. 배포 중 백업은 서버 정지 상태라 DB가 일관됨 |
| 단위 테스트 | 송금·잔액 부족·동시 송금·소수 처리는 **임시 폴더의 파일형 SQLite**로 테스트(`:memory:` DB는 연결을 닫으면 사라져 재기동 검증이 안 됨). 연결을 닫고 다시 열어 잔액·로그 대조 |

성능: `synchronous=FULL`은 커밋마다 디스크 동기화를 해서 메인 스레드가 잠깐 멈출 수 있다. 직업 보상은 블록마다 들어오므로 테스트에서 커밋 시간(목표 p99 < 2ms)을 잰다. 느리면 **입금(직업 보상)만** 짧게 묶어 기록하는 방식을 검토하고, 출금·송금은 항상 커밋 후 성공을 유지한다(입금은 꺼져서 날아가도 대가로 받은 물건이 없지만, 출금은 상품이 이미 나간 뒤라 반드시 기록돼야 함).

Bank 완료 체크리스트 (테스트 서버, 버전은 9.3에 고정한 JAR):

1. **첫 연동 테스트**: 빈 테스트 서버에서 Vault·Bank·VJobs·EconomyShopGUI 로드 확인 → VJobs 보상 입금 → 같은 계정으로 상점 구매 → `/money`로 입금액−구매액 차이가 정확한지 확인. `/bank log`에서 입금은 `source=VJobs`, 구매 출금은 `source=EconomyShopGUI`로 찍히는지도 확인(2.4의 식별 근거)
2. `/pay` 음수·0·소수점·잔액 초과·자기 자신·없는 닉네임 → 모두 거부
3. **강제 종료 대조**: 송금·구매 직후 `docker kill` → 재기동 후 거래마다 대조한다(총액만 보면 거래 전체가 사라진 경우를 놓침).
   - `/pay`: 성공 메시지를 받은 송금마다 양쪽 잔액과 `transactions` 1줄이 모두 있는지
   - 상점: **잔액·Bank 구매 기록·EconomyShopGUI 구매 로그·인벤토리 네 가지를 함께** 대조하고 두 방향을 모두 본다. ① 상품은 있는데 출금 기록이 없음(돈 복사) → 버그, 배포 불가 ② 출금은 됐는데 상품이 없음(돈만 빠짐) → 출금 커밋 후 상품 지급 전, 또는 지급 후 인벤토리 저장 전에 꺼지면 생길 수 있음. 재현되면 2.4 환불 절차로 처리
4. 첫 설치 시 빈 DB 생성, 이후 `bank.db` 삭제·손상 시 잠금 모드로 뜨는지(2.3)
5. 서버 로그에 경고·스택트레이스 없음

### 2.2 소수 금액 규칙

구 Vault API는 금액을 `double`로 주고받는다. 잔액은 정수로만 유지하고, **MVP에서는 소수 금액을 아예 받지 않는다.**

| 경로 | 규칙 |
| --- | --- |
| 직업 보상 | 정수 고정 보상만(5장 표는 전부 정수). VJobs 레벨별 수입 보너스·보상 배율 0% |
| 상점 | 6.3 가격은 전부 정수. EconomyShopGUI의 할인(`discounts`)·판매 배율(`sell-multipliers`)·계절 가격은 쓰지 않음 |
| Vault 입금·출금·`has` | 정수가 아닌 금액이 오면 **입금(`depositPlayer`)·출금(`withdrawPlayer`)은 `EconomyResponse`의 `FAILURE`(사유 "정수 금액만 가능"), `has`는 `false`를 반환**하고 잔액은 그대로. 반올림·올림·잔여분 누적은 하지 않음(표시 가격과 실제 차감액이 달라지고 환불 금액도 어긋나기 때문) |
| `/pay`, `/bank` | 정수만 허용, 소수 입력은 거부 |
| 로그 | 거부한 소수 요청은 호출한 플러그인 이름과 함께 경고 1줄 → 테스트에서 소수가 들어오는 경로를 찾아 설정으로 끔 |

2단계에서 레벨 보너스를 다시 켜려면 이 규칙부터 바꾼다. 그때 잔여분 누적을 넣는다면 누적값 저장과 거래 기록을 같은 트랜잭션에 두고, 8.04원 입금 25회를 중간 재기동을 포함해 201원이 되는지 테스트한다.

### 2.3 첫 설치와 데이터 분실 구분

- **첫 설치**: `plugins/Bank/` 폴더 자체가 없을 때만 빈 `bank.db`를 만들고, `meta`와 `config.yml`에 `installed: true`, 생성 시각을 기록한다.
- **운영 중 분실·손상**: `installed: true`인데 `bank.db`가 없거나 `PRAGMA integrity_check`가 실패하면, 새 DB를 만들지 않고 **잠금 모드**로 뜬다. Vault 제공자는 등록하되 모든 입출금이 실패를 반환하고(상점 구매·직업 보상 정지), OP에게 접속 시 경고. 관리자가 백업에서 복원한 뒤 재시작해야 풀린다.
- **복원 원칙**: Bank 데이터만 과거로 돌리지 않는다. 거래 뒤 Bank만 되돌리면 산 아이템과 돌려받은 돈이 함께 남는다. 복원은 **같은 백업 시점의 월드(플레이어 인벤토리 `playerdata` 포함) + `plugins/`를 함께** 되돌리는 DEPLOY.md의 전체 복원 절차로만 한다.
- JAR 롤백(`rollback.sh`)은 잔액을 바꾸지 않는다. Bank 코드만 이전 버전으로 돌릴 뿐이라 DB 스키마는 하위 호환을 유지한다.
- **경제 복원에 쓰는 백업은 서버 정지 상태에서 만든 것만** 쓴다(`install-plugin.sh`가 만드는 백업, 또는 서버를 멈추고 `backup.sh --offline`). 서버가 켜진 채 만드는 `backup.sh`는 월드를 저장하고 묶는 동안에도 Bank 거래가 계속되므로, 같은 파일 안에서도 인벤토리와 잔액 시점이 어긋날 수 있다.
- 첫 설치 때 `install-plugin.sh`가 자동으로 만드는 백업은 **Bank 설치 전**이라 `bank.db`가 없다. 그래서 설치·권한 검증이 끝난 뒤 오픈 전에 **기준 백업**을 정지 상태로 한 번 남긴다(9.2의 6번).
- 첫 운영 배포 전, 운영 백업으로 만든 복제 서버에서: 구매 1건 → 그 직전의 정지 상태 백업으로 전체 복원 → 잔액과 인벤토리가 함께 구매 전으로 돌아오는지 확인.

### 2.4 구매 유실 환불 절차 (MVP 운영)

출금이 커밋된 뒤 상품 지급이나 인벤토리 저장 전에 서버가 꺼지면 "돈만 빠진" 구매가 생길 수 있다. MVP는 코드로 막지 않고 운영 절차로 처리한다. 구 Vault의 `withdrawPlayer(player, amount)`에는 호출 플러그인 이름도, 상점 거래번호도 없으므로 **Bank가 출금 시점에 식별 근거를 직접 남긴다.**

**출금 때 Bank가 남기는 기록** (`transactions`의 추가 칸)

| 칸 | 내용 | 얻는 방법 |
| --- | --- | --- |
| `source` | 출금을 호출한 플러그인 이름 (예: `EconomyShopGUI`, `Bank`(=`/pay`)) | 호출 스택(`StackWalker`)에서 Bank가 아닌 첫 플러그인 클래스의 클래스로더로 판별. 판별 실패 시 `unknown` |
| `time_ms` | 밀리초 단위 시각 | |
| `boot_id` | 서버 기동마다 새로 만드는 ID | Bank 활성화 시 생성, `meta`에 기록 |
| `context` | 플레이어 위치(월드·좌표)와 그 순간 열려 있던 인벤토리 창 제목 | 출금 시점 `Player` 상태 (오프라인이면 비움) |

**비정상 종료 표시**: Bank는 정상 종료(`onDisable`)에서 `meta.clean_shutdown=<boot_id>`를 쓰고, 켜져 있는 동안 30초마다 `meta.heartbeat=<boot_id, 시각>`을 갱신한다. 다음 기동 때 이전 `boot_id`가 정상 종료로 기록돼 있지 않으면 그 기동을 **비정상 종료**로 기록하고, 마지막 heartbeat 시각을 **장애 추정 시각**(실제 종료는 그 뒤 30초 안)으로 남긴다. 마지막 거래 시각은 장애 시각으로 쓰지 않는다(거래가 뜸하면 몇 시간 전일 수 있음).

**종료 중 장애** (PR #8 리뷰 반영): Paper는 플러그인을 끈 **뒤에** 플레이어를 저장한다. 그래서 `onDisable`의 `clean_shutdown`은 "Bank DB를 정상으로 닫았다"는 뜻일 뿐이고, 그 기동은 `boots.status=closed`로 두고 그 순간의 접속자 목록(`shutdown_players`)과 월드 폴더를 남긴다. 다음 기동에서 그 접속자들의 플레이어 파일(월드 루트의 `players/data/<uuid>.dat`, 예전 구조면 `playerdata/<uuid>.dat`. 26.x의 `getWorldFolder()`는 차원 폴더 `world/dimensions/minecraft/overworld`라 위로 올라가 루트를 구함)이 Bank 종료 시각보다 **확실히 늦게** 저장됐는지(밀리초 값이 있으면 엄격 비교, 초 단위 값이면 다음 초 이후만 인정, 같은 초는 미확인) 확인해서, 모두 저장됐으면 정상 종료, 하나라도 아니면 **비정상 종료**(`unclean_reason=player_save_missing`, 장애 추정 시각 = Bank 종료 시각)로 기록한다. 접속자가 없었으면 정상 종료. `/reload`처럼 서버가 꺼지지 않고 Bank만 꺼진 경우도 저장이 확인되지 않아 비정상으로 잡히지만, 환불 대상이 넓어질 뿐 관리자 확인에서 걸러진다.

**`/bank refund`가 확인하는 조건** (하나라도 아니면 명령이 거부하고 이유를 출력)

1. 거래 종류가 출금이고 `source`가 `EconomyShopGUI` 또는 `Market`(v0.8, 13.6)
2. 그 거래의 `boot_id`가 비정상 종료로 기록된 기동
3. 같은 거래번호로 환불한 적이 없음(`transactions.ref` 유일 제약)

시간 조건은 명령에 넣지 않는다. 플레이어 저장 간격은 Paper 설정(`player-auto-save-rate`, 틱 단위)에 따라 달라서 고정값으로 판정할 수 없다. 대신 아래 관리자 확인에서 근거가 부족하면 보류한다.

**관리자 확인** (아래 근거가 모두 갖춰지지 않으면 **보류**)

1. 플레이어 신고(시각, 상품, 수량)를 받는다.
2. **장애 시점 근거**: 위의 장애 추정 시각이 있고, 서버 로그(`docker logs`)에도 정상 종료 메시지 없이 끊긴 흔적이 있다.
3. **유실 시간대 근거**: 구매 시각이 장애 추정 시각 직전, 운영 서버의 실제 플레이어 저장 간격(`config/paper-global.yml`의 `player-auto-save-rate`와 월드 자동 저장 간격 중 짧은 쪽) 안에 있다. 그보다 이전 구매는 인벤토리가 이미 저장됐을 가능성이 높으므로 보류. 그 플레이어가 구매 뒤 장애 전에 접속을 끊었다면(로그아웃 때 저장됨) 역시 보류.
4. **금액 근거**: 신고한 상품의 6.3 가격 × 수량이 거래 금액과 정확히 같다. 후보가 여러 건이면 `context`(상점 창 제목, 위치)로 좁히고, **그래도 한 건으로 특정되지 않으면 보류.**
5. **상품 부재 근거**: 플레이어 인벤토리·엔더 상자에 그 상품이 없다. 단, 이것만으로는 "지급 후 소비"와 구별되지 않으므로 2–4번 없이 이것만으로 환불하지 않는다. EconomyShopGUI 로그는 참고만 한다(로그도 함께 날아갔을 수 있음).
6. 환불만 하고 상품은 다시 주지 않는다. 환불·보류 결정과 근거를 노션에 한 줄 기록.

보류된 건은 그 금액이 소액(MVP 기준 2,000원 이하, 직업 약 12분치)이면 관리자 판단으로 `/bank give`로 보상하고 기록한다. 그보다 크면 같은 시점의 CoreProtect 기록 등 다른 근거가 나올 때까지 보류한다.

## 3. 시스템 구성

```
플레이어
  ├─ /jobs ...        → VJobs            (돈 공급: 직업 보상)
  ├─ /shop            → EconomyShopGUI   (돈 소비: 구매)
  ├─ /money, /pay, /baltop → Bank (자체) (잔액·송금·순위)
  └─ /economy (1.5단계) → EconomyHub (자체) : 위 명령을 GUI 버튼으로 묶음
                 │
        VaultUnlocked (공통 경제 API)
                 │
        Bank (자체, 경제 제공자)  → plugins/Bank/bank.db (백업 대상)
```

- 잔액은 Bank 한 곳에만 저장한다. 다른 자체 플러그인(EconomyHub, Trade)도 Bank를 직접 부르지 않고 VaultUnlocked API로 조회·입출금한다.
- VJobs 직업 데이터는 VJobs의 SQLite, 상점 가격은 EconomyShopGUI 설정 파일. 둘 다 `plugins/` 아래라 `backup.sh`에 이미 포함된다.

### 5.3 레벨 경험치

- 보상 10원당 경험치 1 → 직업 1시간 ≈ 1,000 XP.
- 레벨 n → n+1 필요 경험치 = `440 × n^0.6` (Lv1→2: 440, Lv10→11: 1,752, Lv30→31: 3,386, Lv49→50: 4,545)
- 누적 소요 시간(Lv1 시작, 직업 1개에 시간당 10,000원 기준):

| 도달 레벨 | 10 | 20 | 30 | 40 | 50 |
| --- | --- | --- | --- | --- | --- |
| 누적 시간 | 10.0h | 31.8h | 61.7h | 98.5h | 141.4h |

- v0.3의 `100 × n^1.5`는 실제로 Lv30 189시간, Lv50 690시간이 걸려 목표와 맞지 않아 교체했다.
- VJobs의 곡선 설정 형식이 이 식을 그대로 못 받으면, 표의 누적 시간에 맞도록 근사한다. 레벨은 MVP에서 보너스가 없어 자랑거리 정도의 의미.

## 6. 서버 상점 (EconomyShopGUI)

### 6.1 차익(무한 수익) 방지 규칙

MVP는 서버 매입(플레이어가 서버에 파는 것)이 없어서 차익이 생길 수 없다. 아래 규칙은 **나중에 매입을 추가할 때** 반드시 지킨다.

1. **매입 가격 ≤ 구매 가격의 25%** (같은 아이템).
2. **조합 차익 금지**: 재료를 사서 만든 결과물의 매입가 ≤ 재료 구매가 합. 반대로 결과물을 사서 분해한 재료의 매입가 합 ≤ 결과물 구매가. (예: 철 블록 ↔ 철 주괴 9개)
3. **제련 차익 금지**: 원석·광석 매입가 ≤ 결과물 매입가가 되지 않게.
4. **자동 생산 가능 자원은 매입하지 않음**: 조약돌·돌·현무암·얼음·모래(가루기)·사탕수수·대나무·호박·수박·켈프·밀·당근·감자·썩은 살점·뼈·실·화약·철(골렘 농장)·금(피글린 농장)·양털·꿀·에메랄드(주민)·청금석·레드스톤(성직자 주민) 등.
5. **주민 거래가와 비교**: 주민에게 싸게 사서 상점에 팔 수 있는 아이템은 매입하지 않는다.

이 규칙을 적용하면 매입 후보는 다이아몬드 같은 재생 불가 자원 정도만 남는다. 돈 공급은 직업 보상이 담당한다.

### 6.2 판매 제외 (돈으로 못 사는 것)

**EconomyShopGUI(`/shop`)에서는** 아래 전부를 팔지 않는다. 이 중 다이아몬드·에메랄드·인챈트 책·경험치 병·황금 사과·엔더 진주는 v0.8부터 **자체 `Market`에서 주간 한도를 걸고** 판다(13장). EconomyShopGUI 무료판은 플레이어별 구매 한도(`stock-limit-player`)가 프리미엄 기능이라 한도를 걸 수 없기 때문이다.

다이아몬드·에메랄드·네더라이트(관련 전부), 다이아·네더라이트 장비, 인챈트 책, 경험치 병, 황금 사과·마법이 부여된 황금 사과, 불사의 토템, 겉날개, 셜커 상자·껍데기, 스포너·스폰 알, 네더의 별·신호기, 트라이던트, 철갑 껍데기, 엔더 진주·엔더의 눈, 커스텀 고성능 장비.

**어디서도 팔지 않는 것**(v0.8에도 유지): 네더라이트 관련 전부(고대 잔해·파편·주괴·강화 대장장이 형판), 다이아·네더라이트 장비 완제품, 마법이 부여된 황금 사과, 불사의 토템, 겉날개, 셜커 상자·껍데기, 스포너·스폰 알, 네더의 별·신호기, 트라이던트, 철갑 껍데기, 엔더의 눈, 커스텀 고성능 장비, 저주 인첸트.

### 6.4 서버 매입 (EconomyShopGUI 판매는 계속 막음)

v0.8부터 서버 매입은 자체 `Market`의 `/판매`로만 연다(14장). **EconomyShopGUI에서는 계속 팔 수 없게** 두 겹으로 막는다. EconomyShopGUI는 직업·직접 획득 여부를 판단할 수 없기 때문이다.

1. `shops.yml`의 모든 상품에 `sell` 키를 두지 않거나 `sell: -1` (공식 지원). 기본 상점 파일은 쓰지 않고 6.3 표로 새로 작성한 파일만 둔다.
2. LuckPerms `default` 그룹에서 판매 명령 권한을 명시적으로 끈다. **이 권한들은 기본값이 true**라 아무것도 안 하면 열려 있다.
   `EconomyShopGUI.sellall`, `EconomyShopGUI.sellallitem`, `EconomyShopGUI.sellallhand`, `EconomyShopGUI.sellgui`를 `false`로 설정한다(명령은 9.2의 4번).
   (`EconomyShopGUI.shop.*`은 구매에도 쓰이므로 건드리지 않는다. 노드 이름은 대소문자를 구분하는 경우가 있어 위키 표기 그대로 쓴다.)

검증: 일반 계정으로 ① 상점 GUI에서 판매 클릭 ② `/sellall` ③ `/sellall hand` ④ `/sellgui`를 각각 시도한 뒤 **아이템 수량과 잔액이 모두 그대로**인지 확인.

- 다이아 유통량 걱정(v0.3): 14장 매입은 직접 캔 것만, 낮은 가격(150원)에서 시작하고 하루 한도가 있어 유통량 급감을 막는다.

### 6.5 가격 산정 예시 (검산)

- 유리 64개 = 1,280원 ≈ 직업 8분치. 직접 만들면 5분 + 연료. → 약간 비싸다(의도).
- 철 주괴 64개 = 9,600원 ≈ 직업 1시간. 같은 1시간 광부를 하면 돈 약 9,000원 + 원석 30개. → 직접 캐는 쪽이 이득(의도).
- 이름표 1,500원 ≈ 9분치. 야생에서는 낚시·던전 운에 달린 아이템이라 돈의 가치가 생김.

### 7.2 `/economy` (EconomyHub) 상세

- 의존: `compileOnly` Vault API, `plugin.yml`에 `depend: [Vault]`, `softdepend: [VJobs, EconomyShopGUI]`
- GUI 27칸: 내 잔액(머리 아이템), 직업 현황(`/jobs` 열기), 상점(`/shop`), 송금 안내(채팅에 `/pay <닉> <금액>` 안내), 부자 순위(`/baltop`, Bank), 이용 가이드(책)

- 아이템 이동 차단: 클릭·드래그·숫자키·Shift 클릭 모두 취소 (NeatSort 등 정렬 플러그인과 충돌 방지 위해 `InventoryHolder` 커스텀 홀더로 식별)

### 7.3 `/trade` 요구사항 (2단계)

- 접속자 목록 GUI(기존 `/tpa` GUI 재사용) → 요청 → 30초 내 수락
- 양쪽 4×4 칸 + 금액 입력, 양쪽 "확인" 후 3초 카운트다운 → 확정
- 내용이 바뀌면 양쪽 확인 해제, 거리 제한 없음, 전투 중(Travel의 전투 태그) 불가
- 로그아웃·사망·서버 종료·인벤토리 닫기 → 즉시 취소, 아이템 원래 주인에게 반환(가득 차면 발밑 드롭)
- 돈은 확정 순간에만 출금·입금(잔액 부족 시 거래 취소). 모든 거래는 로그 파일에 기록

## 9. 배포 절차

Bank는 다른 자체 플러그인처럼 `deploy.ps1 -Plugin bank`로, 외부 플러그인도 같은 `scripts/server/install-plugin.sh`로 설치한다. 이 스크립트는 JAR 안의 `plugin.yml` 이름을 읽어 처리하므로 우리 JAR이 아니어도 되고, 백업 → 정지 → 교체 → 시작 → 로드 확인 → 롤백 기록까지 그대로 쓸 수 있다. Chunky·CoreProtect 보호도 그대로 유지된다.

### 9.1 테스트 (로컬)

1. `.\gradlew :plugins:bank:runServer`로 뜨는 테스트 서버(`plugins/bank/run/`)의 `plugins/`에 9.3에 고정한 외부 JAR 4개(VaultUnlocked·VJobs·EconomyShopGUI·LuckPerms)를 넣고 실행 → 설정 파일 생성
2. 5·6장 값으로 설정을 고치고 재시작, 6.4의 LuckPerms 명령 실행 → 2.1 첫 연동 테스트부터 진행
3. 8장 체크리스트 + 2.1 체크리스트 진행 (TestBot 계정 포함 2인). 벌목꾼은 실제 수동 벌목량(목표 8,000원 = 원목 1,000개/시간, 일반 나무와 **2×2 가문비 + 뼛가루** 두 가지 기준, 1,500개 초과 시 5.2 기준대로 보상 하향)과 **직업 2개 겸업 시 합산 수입**을 따로 잰다
4. Travel·Pets·CustomItems와 함께 켜서 로드 오류 없는지 확인
5. 통과한 설정 폴더 전체(`plugins/VJobs/`, `plugins/EconomyShopGUI/`, `plugins/LuckPerms/`의 설정 파일, 데이터 파일 제외)를 레포 `server-config/economy/`에 커밋

### 9.2 운영

```powershell
# Windows: 1) Bank 먼저 업로드만 (설치는 외부 플러그인과 한 번에)
.\scripts\deploy.ps1 -Plugin bank -SshHost minipc-lan -UploadOnly
# 2) 외부 JAR 업로드
ssh minipc-lan "mkdir -p ~/plugin-staging/economy"
scp .\external\*.jar minipc-lan:~/plugin-staging/economy/
```
```bash
# 미니PC
~/mc-scripts/install-plugin.sh --dry-run ~/plugin-staging/bank-*.jar ~/plugin-staging/economy/*.jar   # 새 플러그인 5개만 나오는지 확인
~/mc-scripts/install-plugin.sh ~/plugin-staging/bank-*.jar ~/plugin-staging/economy/*.jar             # 백업 + 설치 + 재시작
```

**운영 첫 기동부터 검증된 설정으로 뜨게 한다.** 기본 설정으로 한 번 열면 그 사이 접속한 사람이 기본 상품을 팔 수 있다.

1. 위 업로드와 함께 `server-config/economy/`를 미니PC `~/plugin-staging/economy-config/`로 올린다.
2. `install-plugin.sh` 실행 **전에**(서버가 켜져 있어도 됨, 아직 로드 안 된 플러그인 폴더라 서버가 건드리지 않음) 설정을 `plugins/` 아래 각 폴더로 복사하고, 소유자를 기존 `plugins/` 폴더와 같게 맞춘다.
   ```bash
   cp -r ~/plugin-staging/economy-config/. /home/deploy/services/minecraft/data/plugins/
   ```

**오픈 전 접속 제한.** `-Delay 0`은 재시작 공지 대기만 생략할 뿐 접속을 막지 않는다. 설치부터 검증까지는 접속을 따로 막는다.

- 미리 디스코드 등으로 "점검 중 접속 금지"를 공지한다. **OP 계정은 화이트리스트를 무시하고 들어올 수 있으므로** 공지가 실제 차단 수단이다.
- 비OP 계정은 화이트리스트를 임시로 줄여서 막는다. 서버 콘솔에서 `whitelist list`로 명단을 기록해 두고, 관리자 본인만 남긴 뒤(`whitelist remove <닉>`) 9.2의 7번에서 다시 추가한다. itzg 이미지가 `WHITELIST` 환경 변수로 명단을 관리하고 있다면 재시작 때 원래 명단으로 덮어쓸 수 있으니, 3번 재시작 직후 `whitelist list`로 다시 확인한다.

3. `install-plugin.sh`로 설치·재시작. 첫 기동이 곧 최종 설정이다. Bank는 이때 빈 DB를 만든다(2.3).
4. LuckPerms 권한은 설정 파일이 아니라 LuckPerms DB(기본 H2)에 저장되고, 이 DB는 테스트 서버에서 복사해 오지 않는다. 첫 기동 직후 서버 콘솔에서 다음을 실행한다. 이 몇 분 동안에도 1겹(`shops.yml`에 판매가 없음)이 이미 적용돼 있어 팔 수 있는 상품은 없다.
   ```
   lp group default permission set jobs.limit.2 true
   lp group default permission set EconomyShopGUI.sellall false
   lp group default permission set EconomyShopGUI.sellallitem false
   lp group default permission set EconomyShopGUI.sellallhand false
   lp group default permission set EconomyShopGUI.sellgui false
   ```
5. 일반 권한으로 검증한다. 관리자 계정을 잠시 `deop <닉>` 하고 진행한 뒤 콘솔에서 `op <닉>`으로 되돌린다(운영 서버는 정품 인증이라 TestBot 계정은 못 씀).
   - 직업 두 번째 가입 성공, 세 번째 가입 거부
   - 6.4 판매 검증 4가지(아이템·잔액 그대로)
   - 2.1 첫 연동 테스트(직업 보상 → 구매 → `/money` 차액)
6. **기준 백업**: 서버를 멈추고 `backup.sh --offline`으로 정지 상태 백업을 남긴 뒤 다시 켠다(`bank.db`와 권한이 들어간 첫 백업, 2.3).
   ```bash
   docker stop -t 90 minecraft-paper && ~/mc-scripts/backup.sh --offline && docker start minecraft-paper
   ```
7. 화이트리스트 명단을 원래대로 되돌리고(`whitelist add <닉>`) 오픈 공지를 한다.

- 설정 복사는 `/reload` 없이 재시작으로 반영(기존 원칙 유지).
- 되돌리기: `~/mc-scripts/rollback.sh`는 JAR만 원복하고 잔액은 그대로다. 잔액을 과거로 돌려야 하면 Bank 폴더만이 아니라 같은 시점의 전체 백업을 복원한다(2.3).
- 오픈 공지: 노션에 명령어표(`/jobs`, `/shop`, `/money`, `/pay`, `/baltop`, 이후 `/economy`).

### 9.3 설정 파일 관리

- `server-config/economy/<플러그인>/`에 실제 운영 설정을 커밋. 가격 변경은 PR로 남긴다(이 문서 6장과 같이 수정).
- 외부 플러그인 버전은 `server-config/economy/VERSIONS.md`에 **JAR 파일명·버전·SHA-256**으로 고정하고, 테스트한 그 JAR만 운영에 올린다. 서버 업데이트 시 26.x 지원 여부를 먼저 확인.

| 플러그인 | 고정 버전 | plugin.yml `name` |
| --- | --- | --- |
| VaultUnlocked | 2.20.3 | `Vault` |
| VJobs | 2.2.0-RELEASE | 테스트 때 확인 |
| EconomyShopGUI (무료) | 테스트 때 받은 최신 | 테스트 때 확인 |
| LuckPerms | 테스트 때 받은 최신(Bukkit) | `LuckPerms` |

## 13. 희귀 상점과 인첸트 책 뽑기 (v0.8 기획 변경)

> 상태: **확정**(2026-11-25, 13.8). 다음은 `plugins/market` 개발.

### 13.1 왜 바꾸나

- 유저들이 순수 야생보다 **돈을 모아서 쓰는 콘텐츠**를 더 원한다.
- v0.7까지는 돈을 쓸 곳이 건축 블록·음식 정도라, 직업을 꾸준히 하는 사람은 잔액만 쌓인다(소비처 부족 → 돈의 가치 하락). 희귀품과 뽑기는 **강한 소비처**라 쌓이는 돈을 흡수한다.
- 돈이 생기는 곳은 직업 보상과, 14장의 직업별 매입(직접 얻은 것만)뿐이다. 상점·희귀 상점에서 산 물건은 매입 대상이 아니므로(14.2) 희귀품을 팔아도 "사서 되팔아 돈 복사" 같은 순환은 생기지 않는다.

### 13.2 경제 밸런스 영향

기준: 직업 1시간 ≈ 10,000원(4.1), 하루 2시간 하는 사람 ≈ 하루 20,000원, 주 140,000원.

| 영향 | 판단 | 대응 |
| --- | --- | --- |
| 통화량 | 소비가 크게 늘어남 → 인플레이션 억제. 14장 매입이 공급을 직업별로 시간당 15–50% 늘리지만(하루 5,000원 한도) 희귀 상점·뽑기 소비가 더 큼 | 10장에 희귀 상점·뽑기 지표 추가 |
| 다이아 가치 | 상점가가 생기면 플레이어 간 거래가의 **상한**이 된다(그 이상 주고 살 사람이 없음) | 상점가를 "직접 캐는 것"보다 비싸게 + 주간 한도 |
| 광부 직업 | 광부 1시간 = 다이아 약 8개 + 8,800원. 같은 1시간 다른 직업 10,000원으로는 다이아 6개(1,500원 기준)밖에 못 삼 → **직접 캐는 쪽이 계속 이득** | 다이아 가격은 1,500원 이상 유지 |
| 장비 성장 속도 | 다이아 장비 풀세트(약 24개) 직접 채굴 ≈ 3시간. 상점만으로는 주간 한도 16개라 최소 2주 → 상점은 "보조 수단" | 한도로 속도 조절 |
| 인첸트 | 주민 사서 거래·인첸트 테이블이 원래 주 경로. 상점·뽑기는 이를 빠르게 할 뿐이고, 모루 경험치 비용은 그대로 남는 2차 소비처 | 수선은 고정가 판매 안 함(13.4) |
| 상위권 독주 | 수입이 많은 사람이 희귀품을 싹쓸이 | 1인 주간 한도, 뽑기 하루 한도 |
| 사행성 | 현금 결제가 없으므로 현실 돈 문제는 없음. 그래도 과몰입 방지 | 확률 공개, 하루 한도, 천장(13.5) |

결론: 유저 말대로 **희귀품 판매는 소비를 늘리는 방향**이고, 가격을 "직접 구하는 것보다 비싸게" + 주간 한도만 지키면 야생 가치도 크게 해치지 않는다.

소비 흡수량 예시(1인 주간 최대): 다이아 16개 24,000원 + 인첸트 책 5권 약 20,000원 + 기타 희귀품 약 20,000원 + 뽑기(하루 최대 20회) 최대 280,000원. 주 수입 140,000원인 사람의 돈을 충분히 흡수할 수 있다. 뽑기가 흡수의 대부분을 맡는다.

### 13.6 구현: 자체 `Market` 플러그인 (권장)

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| EconomyShopGUI에 추가 | 설정만으로 끝. 무료판도 인첸트 책(`enchantments: - "efficiency:4"`) 판매 가능 | 플레이어별 한도(`stock-limit-player`)·구매 시 명령(`buy-commands`)은 **프리미엄 전용**, 랜덤 지급 기능 없음 → 한도·뽑기 불가 | 희귀품에는 부적합 |
| 외부 상자(crate) 플러그인 | 기능 많음 | 26.3을 명시한 검증된 플러그인을 아직 못 찾음, Bank 환불 절차(2.4)와 연동 안 됨 | 보류 |
| **자체 `plugins/market`** | 주간 한도·천장·확률 공개·로그를 우리가 통제. Bank처럼 출금 기록과 대조 가능 | 개발 5–7일(매입 포함, 7.1) | **권장** |

**`plugins/market` (플러그인 이름 `Market`)**

- 의존: `depend: [Vault]`. Bank를 직접 부르지 않고 Vault API로 출금(3장 원칙).
- 명령: `/희귀상점` (`/market`), `/뽑기` (`/gacha`), `/뽑기 확률`. 관리자: `/market reload`, `/market log <닉>`, `/market reset <닉>`(한도 초기화), 권한 `market.admin`.
- 저장: `plugins/Market/market.db` (파일형 SQLite, Bank와 같은 WAL·`synchronous=FULL`). `purchases(id, time_ms, uuid, item, amount, price, week_key, bank_ref)`, `pulls(id, time_ms, uuid, tier, enchant, level, price, pity_before, bank_ref)`, `pity(uuid, count)`.
- 처리 순서 (구매·뽑기 공통):
  1. 인벤토리 빈칸·한도·잔액 확인 → 하나라도 안 되면 거부(돈 안 빠짐)
  2. 뽑기면 서버에서 결과 확정(`SecureRandom`, 천장 반영)
  3. Vault 출금 → 실패하면 중단
  4. 한 SQL 트랜잭션으로 구매/뽑기 기록 + 한도 + 천장 카운터 갱신
  5. 아이템 지급. 결과 화면은 연출일 뿐 창을 닫거나 로그아웃해도 결과는 이미 확정
- 3–5 사이에 서버가 꺼지면 2.4와 같은 "돈만 빠진" 경우가 생긴다. Bank `/bank refund`의 `source` 조건에 `Market`을 추가하고(2.4 수정), 관리자는 `market.db`의 기록(시각·품목·금액이 정확히 남음)으로 대조한다. EconomyShopGUI보다 근거가 확실하다.
- 정수 가격만(2.2). 확률은 설정 파일 `config.yml`의 등급별 `weight`(정수, 합 10,000 = 100.00%)로 두고, 로드 시 합이 10,000이 아니거나 등급 안 책 목록이 비면 **뽑기를 잠근다**.

## 14. 서버 매입: 기본가 + 직업 보너스 (v0.8 기획 변경)

> 상태: **확정**(2026-11-25, 14.8). 6.4의 "MVP 매입 없음"을 바꾼다. EconomyShopGUI의 판매 기능은 계속 끄고(6.4), 매입은 자체 `Market`의 `/판매`로만 한다.
> 2026-11-25 개편: "내 직업 품목만 판매"에서 **"모든 매입 품목을 기본가로 판매 + 내 직업 품목은 직업 보너스"**로 바꿨다. 대형 서버에 익숙한 유저에게 "못 판다"보다 "내 직업이면 더 받는다"가 거부감이 적다. 직업 보유 시 받는 금액은 이전 확정가와 같다.

### 14.1 규칙

1. 매입 품목(14.4)은 **누구나 기본가로** 팔 수 있다.
2. **내 직업 2개의 품목은 직업 보너스**(+100–200%, 직업별)가 붙은 가격으로 판다. 단, 그 직업에 가입해 있는 동안 직접 얻은 수량만(14.2).
3. **내가 직접 얻은 것만** 판다. 상점에서 산 것, 자동 농장·주민 거래·상자 전리품으로 얻은 것은 못 판다. 남에게 받은 물건은 본인 판매 가능량만큼만 팔린다.
4. 가격은 **처음엔 보수적으로**, 운영 지표를 보고 단계적으로 올린다(14.5).
5. 1인 **하루 판매 한도**는 모든 품목 합산 5,000원(1단계). 기본가 판매를 열어도 1인 최대 유입량은 그대로다.

효과: 누구나 남는 생산품을 조금은 돈으로 바꿀 수 있고, 제대로 벌려면 직업 품목에 집중해야 해서 분업 동기가 유지된다. 내 직업 밖의 물건은 직접 만들거나 다른 유저에게 사야 하므로 `/trade`를 2단계로 앞당긴다(14.8).

### 14.2 "직접 얻었는지" 판정: 판매 가능량 기록

아이템에 표시(NBT)를 붙이는 대신, **플레이어별로 "직접 얻은 수량"을 DB에 기록**하고 팔 때 그만큼 차감한다.

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 아이템에 획득자 표시(PDC) | 아이템마다 출처가 정확 | 표시가 있는 아이템과 없는 아이템이 **겹쳐지지 않음**(같은 다이아가 두 칸으로 나뉨), 정렬 플러그인·상자·화로와 충돌, 녹이거나 조합하면 표시가 사라짐 | 비권장 |
| **판매 가능량 기록** | 아이템은 바닐라 그대로(겹치기·보관 정상), 구현 단순 | "어느 다이아가 내 것인지"는 구분 안 함. 단, 팔 수 있는 총량은 **내가 직접 생산한 양을 넘지 못하므로** 결과는 같음 | **채택** |

**기록은 직업과 상관없이 모든 플레이어에게** 남기되, 얻은 순간 그 품목의 직업에 가입해 있었는지로 두 칸에 나눠 쌓는다.

- `job_amount`: 그 직업에 가입한 상태로 얻은 수량 → **보너스가**로 판매
- `base_amount`: 가입하지 않은 상태로 얻은 수량 → **기본가**로 판매

예: 낚시꾼이 아닌 광부가 대구 10마리를 낚으면 `base_amount[대구] += 10`(기본가 4원). 나중에 낚시꾼으로 바꿔도 이 10마리는 기본가 그대로다. 그래서 **"직업 없이 모아 두었다가 직업만 바꿔 보너스로 파는" 우회가 원천적으로 안 된다.** 직업을 탈퇴하면 그 직업의 `job_amount`는 `base_amount`로 옮겨진다(삭제하지 않음, 보너스만 사라짐).

**기록되는 경우**

| 카테고리 | 기록 조건 | 기록 안 됨 |
| --- | --- | --- |
| 광부 | 자연 생성 광석을 플레이어가 캐서 떨어진 아이템(행운 포함 실제 드롭 수) | 설치한 광석, 실크터치로 캔 광석 블록, 피스톤으로 옮긴 광석 |
| 벌목꾼 | 플레이어가 벤 자연·묘목 성장 원목 | 설치한 원목 |
| 농부 | 다 자란 작물을 플레이어가 수확한 드롭, 줄기에서 자란 호박·수박 블록 | 덜 자란 작물, 피스톤·주민·물 수확, 설치한 호박·수박 |
| 사냥꾼 | 플레이어가 막타를 친 자연 스폰 몹의 드롭 | 스포너 몹(`fromMobSpawner`), 동물·주민 |
| 낚시꾼 | 낚시로 건진 아이템(`PlayerFishEvent` CAUGHT_FISH) | AFK 판정 중 낚시 |

- 설치 블록 추적: `Market`이 광석·원목·호박·수박 설치 위치를 청크 PDC에 기록한다(VJobs와 같은 방식, 재시작 후에도 유지). 피스톤으로 밀린 블록은 기록 좌표를 함께 옮기거나(`BlockPistonExtendEvent`/`RetractEvent`), 움직인 블록을 판매 가능량 기록 대상에서 제외한다. VJobs의 기록을 읽는 API가 있으면 그걸 쓴다(테스트 서버에서 확인).
- 제련품은 사지 않는다: 철·금·구리는 **원석**(raw)으로만 매입. 블록 형태(다이아 블록 등)도 매입 안 함.
- 직업 변경 쿨타임 24시간(5.1)은 유지한다. 우회 방지는 위 두 칸 기록이 맡고, 쿨타임은 잦은 직업 변경 자체를 줄이는 용도다.
- 플레이어 직업 조회: VJobs API 또는 PlaceholderAPI로 현재 직업 2개를 읽는다(14.8 1순위 확인).
- **탈퇴 이관 보정**: VJobs에 탈퇴 이벤트가 없거나 DB·PlaceholderAPI로 우회하면 탈퇴 순간을 못 잡을 수 있다. 그래서 **접속할 때와 `/판매`를 열 때마다** 현재 직업을 조회해, 보유하지 않은 직업 카테고리에 `job_amount > 0`이 남아 있으면 그 자리에서 `base_amount`로 옮긴다. 판매 직전에도 같은 확인을 한다. 탈퇴 이벤트가 있어도 이 보정은 그대로 둔다.

### 14.3 판매 처리 순서 (`/판매` GUI)

1. 5개 카테고리 탭을 모두 보여준다. 내 직업 2개 탭은 초록색으로 강조하고 `[직업 보너스 +150% 적용 중]`, `기본 4원 → 10원`처럼 함께 표시한다.
2. 품목마다 "가진 수량 / 보너스 판매 가능량 / 기본 판매 가능량 / 오늘 남은 한도"를 표시한다.
3. **보너스분부터, 묶음 단위로 따로** 계산한다. 한 묶음 안에서 두 칸을 섞지 않는다(섞으면 감자 16개 묶음이 6.5원처럼 소수가 됨). 모두 정수 나눗셈:
   1. 보너스 묶음 수 = min(인벤토리 ÷ 단위, `job_amount` ÷ 단위, 남은 한도 ÷ 묶음당 보너스가)
   2. 기본 묶음 수 = min(남은 인벤토리 ÷ 단위, `base_amount` ÷ 단위, 남은 한도 ÷ 묶음당 기본가)
   3. 한 번에 둘 다 팔리면 `sales`에 `price_type`별로 1줄씩(총 2줄) 기록
4. 인벤토리에서 아이템 제거 → Vault 입금 → 한 트랜잭션으로 판매 기록 + 판매 가능량 차감 + 하루 한도 갱신
5. 입금이 실패하면 아이템과 판매 가능량을 되돌린다
6. 정수 가격만(2.2). 싼 품목은 **묶음 단위 가격**(예: 감자 16개당 기본 4원, 보너스 8원)으로 두고 묶음 단위로만 판다

강제 종료 시 "아이템은 빠졌는데 돈이 안 들어온" 경우는 2.4와 같은 방식으로 `market.db` 기록과 대조해 `/bank give`로 처리한다(출금이 아니라 입금 누락이라 `/bank refund` 대상은 아님).

### 14.5 단계별 인상 계획

| 단계 | 시점 | 배율 (대상 직업의 보너스가에만) | 하루 한도 |
| --- | --- | --- | --- |
| 1 | 매입 오픈 | ×1 (14.4) | 5,000원 |
| 2 | 1단계 2주 후 | 대상 직업만 ×1.5 | 7,500원 |
| 3 | 2단계 2주 후 | 대상 직업만 ×2 | 10,000원 |

- **배율은 보너스가에만 곱한다.** 기본가는 그대로 두어, 부진한 직업의 메리트만 키운다.
- **전 직업을 똑같이 올리지 않는다.** 직전 기간 데이터에서 **하루 한도 소진율이 낮고 목표 비율(14.4)에 못 미치는 직업만** 올린다. 목표 비율을 넘은 직업은 그대로 두거나 내린다.
- 인상 조건: 총 통화량 증가가 희귀 상점·뽑기 소비로 흡수되고 있고(10장), 다이아 시세가 무너지지 않음.
- 배율을 곱한 단가는 **정수로 내림**(2.2). 예: 원목 보너스가 3원 ×1.5 = 4원. 이 계산은 문서 PR에서 하고, `config.yml`에는 결과 정수만 적는다(14.7).
- 어느 단계에서도 품목별 **상한(상점 구매가의 25%)**을 넘지 않는다. 특히 **에메랄드는 최대 75원**, 원목 5원, 이름표 375원, 안장 300원에서 멈춘다.
- 내리는 것은 바로 할 수 있게, 올리는 것은 이 문서를 고치는 PR로만.

### 14.6 다른 장과의 관계

- **6.1 1번(매입가 ≤ 구매가 25%)**: 14.4의 품목별 상한으로 단계 인상 후에도 지킨다(에메랄드 75원 등).
- **6.1 4번(자동 생산 자원 매입 금지)**: 판매 가능량은 플레이어가 직접 캔·수확한·잡은 것만 기록하므로, 철 골렘 농장·피글린 금 농장·주민 생산분은 애초에 팔 수 없다. 그래서 철·금 원석처럼 농장으로도 얻을 수 있는 자원도 "직접 캔 원석"에 한해 매입한다.
- **4.1 경제 기준**: 매입은 새 돈 공급원이다(1장 5번 원칙의 근거 문서가 이 장). 1단계 기준 직업 + 보너스가 매입 합산 시간당 약 8,300원(사냥꾼)–11,000원(벌목꾼), 하루 한도 5,000원이 상한.
- **2.4 환불**: 매입은 입금이라 `/bank refund` 대상이 아니다. `market.db` 판매 기록으로 확인 후 `/bank give`.

### 14.7 구현

`plugins/market`(13.6)에 `/판매`(`/sell`)를 추가한다. 추가 DB 테이블: `sell_quota(uuid, item, job_amount, base_amount)`, `sales(id, time_ms, uuid, item, amount, price_type(base|bonus), unit_price, total, bank_ref)`, `daily_sales(uuid, day_key, total)`. 품목→카테고리(직업) 매핑, 묶음 단위, 한도는 `config.yml`. **가격은 배율을 런타임에 곱하지 않고** 품목마다 `base_price`·`bonus_price`·`max_price`를 계산·내림·상한 적용이 끝난 **최종 정수값으로 직접** 적는다(단계 인상은 어차피 이 문서 PR로만 하므로, 그 PR에서 표와 `config.yml`을 같이 고침). 로드 검증은 정수 여부와 `base_price ≤ bonus_price ≤ max_price`만 확인하고, 하나라도 어긋나면 매입을 잠근다. 개발은 희귀 상점·뽑기 2–3일 + 매입 3–4일, 합쳐 **5–7일**(7.1).

악용 체크(8장에 추가): 설치 광석 재채굴, 실크터치 → 설치 → 행운 채굴, 상점 구매품 판매 시도, **비직업으로 모은 뒤 직업 가입 → 보너스가로 판매 시도(기본가로만 팔려야 함)**, 직업 탈퇴 → 보너스가 판매 시도(기본가로만), 하루 한도 직전 연타, 판매 중 강제 종료.
