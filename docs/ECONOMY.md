## 1. 목표와 원칙

야생 활동(채굴·벌목·농사·사냥·낚시)으로 돈(원)을 벌고, 서버 상점·플레이어 거래·치장 콘텐츠에 쓰는 구조를 추가한다.

1. 야생 플레이의 재미와 아이템 가치를 해치지 않는다. **희귀품은 직접 구하는 것보다 비싸게, 주간 한도 안에서만 판다**(v0.8, 13장). 네더라이트·겉날개·토템 같은 최상위 보상은 여전히 돈으로 못 산다.
2. 검증된 외부 플러그인을 쓰고, 서버만의 차별점만 직접 만든다.
3. 화폐는 하나(원). 잔액은 자체 `Bank` 플러그인이 관리하고, 모든 플러그인은 VaultUnlocked를 통해 같은 잔액을 본다.
4. 경제 활동은 선택. 안 해도 야생 플레이에 손해가 없다.
5. **돈이 생기는 곳(공급)은 직업 보상 하나로 시작**하고(v0.8: 직업별 서버 매입을 두 번째 공급원으로 추가, 근거는 14장), 돈이 사라지는 곳(소비)은 상점·치장으로 둔다. 공급원을 늘릴 때는 문서로 근거를 남긴다.
6. 기존 월드·플레이어 데이터와 Travel·Pets·CustomItems를 건드리지 않는다.

### 2.1 화폐는 자체 `Bank` 플러그인으로 (확정)

돈 데이터는 한번 꼬이면 되돌리기 어렵고, 26.3을 명시한 쓸 만한 경제 플러그인이 없다(EssentialsX는 26.1.2, ExcellentEconomy(구 CoinsEngine)는 26.2·NightCore 필요, TheNewEconomy는 유지보수 종료, NexoriaEconomy는 검증 부족). 그래서 처음부터 직접 만든다. 서버 버전을 올릴 때도 우리가 바로 맞출 수 있다.

**`plugins/bank` (플러그인 이름 `Bank`)**

| 항목 | 내용 |
| --- | --- |
| 역할 | VaultUnlocked에 **경제 제공자(Economy provider)** 로 등록. VJobs·EconomyShopGUI·자체 플러그인이 모두 이 잔액을 씀 |
| 연동 | `depend: [Vault]`. VaultUnlocked 2.20.3의 `plugin.yml`은 이름이 `Vault`이고 `VaultUnlocked` 별칭이 없다(2026-11-25 확인). 구 Vault `net.milkbowl.vault.economy.Economy` 인터페이스만 구현(VJobs·EconomyShopGUI가 쓰는 쪽). 첫 연동 테스트(아래 1번)가 통과하면 MVP에 Vault 2 API는 넣지 않는다 |
| 금액 | 잔액은 `long` 정수 원. 표시는 `12,340원`. 소수 처리 규칙은 아래 2.2 |
| 저장 | `plugins/Bank/bank.db` (파일형 SQLite, `journal_mode=WAL`, `synchronous=FULL`). `accounts(uuid, name, balance, updated_at)`, `transactions(id, time_ms, type, from_uuid, to_uuid, amount, from_balance_after, to_balance_after, source, boot_id, context, ref)`, `boots(boot_id, started_ms, last_heartbeat_ms, ended_ms, crash_estimated_ms, status, world_dir, unclean_reason)`, `shutdown_players(boot_id, uuid)`, `meta(key, value)`. `/pay`는 한 줄에 양쪽 잔액이 필요해서 `balance_after`를 `from_`/`to_` 두 칸으로 나눔. `boots`는 기동별 정상·비정상 종료 판정(2.4) |
| 쓰기 방식 | **모든 잔액 변경은 "잔액 검사 → 변경 → 거래 기록"을 한 SQL 트랜잭션으로 처리하고, 커밋이 끝난 뒤에만 성공을 반환한다.** 메모리 캐시는 커밋 후에 갱신하는 조회용 사본. 커밋이 실패하면 Vault에 실패를 반환(상점은 상품을 주지 않음). `/pay`도 출금·입금·로그가 한 트랜잭션. Vault 호출이 다른 스레드에서 와도 되도록 DB 연결 하나를 락으로 보호 |
| 명령 | `/money` (`/bal`, `/돈`): 내 잔액 · `/money <닉>`: 남의 잔액 · `/pay <닉> <금액>` · `/baltop [쪽]` (10명씩, 1분 캐시) |
| 관리자 | `/bank give·take·set <닉> <금액>`, `/bank log <닉> [쪽]`, `/bank refund <거래번호>` (해당 출금을 한 번만 환불, 2.4), `/bank reload` (권한 `bank.admin`, 기본 OP) |
| 송금 규칙 | 최소 10원, **정수만**(소수점 입력 거부), 잔액 초과·자기 자신·음수·0 거부, 오프라인 대상 허용(서버에 한 번이라도 접속한 플레이어만) |
| 로그 | 모든 입출금을 거래마다 1줄씩 `transactions`에 기록. `/bank log`로 조회 |
| 첫 설치 vs 분실 | 2.3 |
| 백업 | `plugins/Bank/`가 `backup.sh` 대상에 이미 포함. 배포 중 백업은 서버 정지 상태라 DB가 일관됨 |
| 단위 테스트 | 송금·잔액 부족·동시 송금·소수 처리는 **임시 폴더의 파일형 SQLite**로 테스트(`:memory:` DB는 연결을 닫으면 사라져 재기동 검증이 안 됨). 연결을 닫고 다시 열어 잔액·로그 대조 |

성능: `synchronous=FULL`은 커밋마다 디스크 동기화를 해서 메인 스레드가 잠깐 멈출 수 있다. 직업 보상은 블록마다 들어오므로 테스트에서 커밋 시간(목표 p99 < 2ms)을 잰다. 느리면 **입금(직업 보상)만** 짧게 묶어 기록하는 방식을 검토하고, 출금·송금은 항상 커밋 후 성공을 유지한다(입금은 꺼져서 날아가도 대가로 받은 물건이 없지만, 출금은 상품이 이미 나간 뒤라 반드시 기록돼야 함).

Bank 완료 체크리스트 (테스트 서버, 버전은 9.3에 고정한 JAR):

1. **첫 연동 테스트**: 빈 테스트 서버에서 Vault·Bank·VJobs·EconomyShopGUI 로드 확인 → VJobs 보상 입금 → 같은 계정으로 상점 구매 → `/money`로 입금액−구매액 차이가 정확한지 확인. `/bank log`에서 입금은 `source=VJobs`, 구매 출금은 `source=EconomyShopGUI`로 찍히는지도 확인(2.4의 식별 근거)
2. `/pay` 음수·0·소수점·잔액 초과·자기 자신·없는 닉네임 → 모두 거부
3. **강제 종료 대조**: 송금·구매 직후 `docker kill` → 재기동 후 거래마다 대조한다(총액만 보면 거래 전체가 사라진 경우를 놓침).
   - `/pay`: 성공 메시지를 받은 송금마다 양쪽 잔액과 `transactions` 1줄이 모두 있는지
   - 상점: **잔액·Bank 구매 기록·EconomyShopGUI 구매 로그·인벤토리 네 가지를 함께** 대조하고 두 방향을 모두 본다. ① 상품은 있는데 출금 기록이 없음(돈 복사) → 버그, 배포 불가 ② 출금은 됐는데 상품이 없음(돈만 빠짐) → 출금 커밋 후 상품 지급 전, 또는 지급 후 인벤토리 저장 전에 꺼지면 생길 수 있음. 재현되면 2.4 환불 절차로 처리
4. 첫 설치 시 빈 DB 생성, 이후 `bank.db` 삭제·손상 시 잠금 모드로 뜨는지(2.3)
5. 서버 로그에 경고·스택트레이스 없음

### 2.2 소수 금액 규칙

구 Vault API는 금액을 `double`로 주고받는다. 잔액은 정수로만 유지하고, **MVP에서는 소수 금액을 아예 받지 않는다.**

| 경로 | 규칙 |
| --- | --- |
| 직업 보상 | 정수 고정 보상만(5장 표는 전부 정수). VJobs 레벨별 수입 보너스·보상 배율 0% |
| 상점 | 6.3 가격은 전부 정수. EconomyShopGUI의 할인(`discounts`)·판매 배율(`sell-multipliers`)·계절 가격은 쓰지 않음 |
| Vault 입금·출금·`has` | 정수가 아닌 금액이 오면 **입금(`depositPlayer`)·출금(`withdrawPlayer`)은 `EconomyResponse`의 `FAILURE`(사유 "정수 금액만 가능"), `has`는 `false`를 반환**하고 잔액은 그대로. 반올림·올림·잔여분 누적은 하지 않음(표시 가격과 실제 차감액이 달라지고 환불 금액도 어긋나기 때문) |
| `/pay`, `/bank` | 정수만 허용, 소수 입력은 거부 |
| 로그 | 거부한 소수 요청은 호출한 플러그인 이름과 함께 경고 1줄 → 테스트에서 소수가 들어오는 경로를 찾아 설정으로 끔 |

2단계에서 레벨 보너스를 다시 켜려면 이 규칙부터 바꾼다. 그때 잔여분 누적을 넣는다면 누적값 저장과 거래 기록을 같은 트랜잭션에 두고, 8.04원 입금 25회를 중간 재기동을 포함해 201원이 되는지 테스트한다.

### 2.3 첫 설치와 데이터 분실 구분

- **첫 설치**: `plugins/Bank/` 폴더 자체가 없을 때만 빈 `bank.db`를 만들고, `meta`와 `config.yml`에 `installed: true`, 생성 시각을 기록한다.
- **운영 중 분실·손상**: `installed: true`인데 `bank.db`가 없거나 `PRAGMA integrity_check`가 실패하면, 새 DB를 만들지 않고 **잠금 모드**로 뜬다. Vault 제공자는 등록하되 모든 입출금이 실패를 반환하고(상점 구매·직업 보상 정지), OP에게 접속 시 경고. 관리자가 백업에서 복원한 뒤 재시작해야 풀린다.
- **복원 원칙**: Bank 데이터만 과거로 돌리지 않는다. 거래 뒤 Bank만 되돌리면 산 아이템과 돌려받은 돈이 함께 남는다. 복원은 **같은 백업 시점의 월드(플레이어 인벤토리 `playerdata` 포함) + `plugins/`를 함께** 되돌리는 DEPLOY.md의 전체 복원 절차로만 한다.
- JAR 롤백(`rollback.sh`)은 잔액을 바꾸지 않는다. Bank 코드만 이전 버전으로 돌릴 뿐이라 DB 스키마는 하위 호환을 유지한다.
- **경제 복원에 쓰는 백업은 서버 정지 상태에서 만든 것만** 쓴다(`install-plugin.sh`가 만드는 백업, 또는 서버를 멈추고 `backup.sh --offline`). 서버가 켜진 채 만드는 `backup.sh`는 월드를 저장하고 묶는 동안에도 Bank 거래가 계속되므로, 같은 파일 안에서도 인벤토리와 잔액 시점이 어긋날 수 있다.
- 첫 설치 때 `install-plugin.sh`가 자동으로 만드는 백업은 **Bank 설치 전**이라 `bank.db`가 없다. 그래서 설치·권한 검증이 끝난 뒤 오픈 전에 **기준 백업**을 정지 상태로 한 번 남긴다(9.2의 6번).
- 첫 운영 배포 전, 운영 백업으로 만든 복제 서버에서: 구매 1건 → 그 직전의 정지 상태 백업으로 전체 복원 → 잔액과 인벤토리가 함께 구매 전으로 돌아오는지 확인.

### 2.4 구매 유실 환불 절차 (MVP 운영)

출금이 커밋된 뒤 상품 지급이나 인벤토리 저장 전에 서버가 꺼지면 "돈만 빠진" 구매가 생길 수 있다. MVP는 코드로 막지 않고 운영 절차로 처리한다. 구 Vault의 `withdrawPlayer(player, amount)`에는 호출 플러그인 이름도, 상점 거래번호도 없으므로 **Bank가 출금 시점에 식별 근거를 직접 남긴다.**

**출금 때 Bank가 남기는 기록** (`transactions`의 추가 칸)

| 칸 | 내용 | 얻는 방법 |
| --- | --- | --- |
| `source` | 출금을 호출한 플러그인 이름 (예: `EconomyShopGUI`, `Bank`(=`/pay`)) | 호출 스택(`StackWalker`)에서 Bank가 아닌 첫 플러그인 클래스의 클래스로더로 판별. 판별 실패 시 `unknown` |
| `time_ms` | 밀리초 단위 시각 | |
| `boot_id` | 서버 기동마다 새로 만드는 ID | Bank 활성화 시 생성, `meta`에 기록 |
| `context` | 플레이어 위치(월드·좌표)와 그 순간 열려 있던 인벤토리 창 제목 | 출금 시점 `Player` 상태 (오프라인이면 비움) |

**비정상 종료 표시**: Bank는 정상 종료(`onDisable`)에서 `meta.clean_shutdown=<boot_id>`를 쓰고, 켜져 있는 동안 30초마다 `meta.heartbeat=<boot_id, 시각>`을 갱신한다. 다음 기동 때 이전 `boot_id`가 정상 종료로 기록돼 있지 않으면 그 기동을 **비정상 종료**로 기록하고, 마지막 heartbeat 시각을 **장애 추정 시각**(실제 종료는 그 뒤 30초 안)으로 남긴다. 마지막 거래 시각은 장애 시각으로 쓰지 않는다(거래가 뜸하면 몇 시간 전일 수 있음).

**종료 중 장애** (PR #8 리뷰 반영): Paper는 플러그인을 끈 **뒤에** 플레이어를 저장한다. 그래서 `onDisable`의 `clean_shutdown`은 "Bank DB를 정상으로 닫았다"는 뜻일 뿐이고, 그 기동은 `boots.status=closed`로 두고 그 순간의 접속자 목록(`shutdown_players`)과 월드 폴더를 남긴다. 다음 기동에서 그 접속자들의 플레이어 파일(월드 루트의 `players/data/<uuid>.dat`, 예전 구조면 `playerdata/<uuid>.dat`. 26.x의 `getWorldFolder()`는 차원 폴더 `world/dimensions/minecraft/overworld`라 위로 올라가 루트를 구함)이 Bank 종료 시각보다 **확실히 늦게** 저장됐는지(밀리초 값이 있으면 엄격 비교, 초 단위 값이면 다음 초 이후만 인정, 같은 초는 미확인) 확인해서, 모두 저장됐으면 정상 종료, 하나라도 아니면 **비정상 종료**(`unclean_reason=player_save_missing`, 장애 추정 시각 = Bank 종료 시각)로 기록한다. 접속자가 없었으면 정상 종료. `/reload`처럼 서버가 꺼지지 않고 Bank만 꺼진 경우도 저장이 확인되지 않아 비정상으로 잡히지만, 환불 대상이 넓어질 뿐 관리자 확인에서 걸러진다.

**`/bank refund`가 확인하는 조건** (하나라도 아니면 명령이 거부하고 이유를 출력)

1. 거래 종류가 출금이고 `source`가 `EconomyShopGUI`. **`Market` 출금은 거부**하고 `/market resolve <거래 ID> refund`를 안내한다(v0.9.2, 13.6). Bank만 환불하면 `market.db` 주문이 지급 대기로 남아 상품까지 지급되기 때문
2. 그 거래의 `boot_id`가 비정상 종료로 기록된 기동
3. 같은 거래번호로 환불한 적이 없음(`transactions.ref` 유일 제약)

시간 조건은 명령에 넣지 않는다. 플레이어 저장 간격은 Paper 설정(`player-auto-save-rate`, 틱 단위)에 따라 달라서 고정값으로 판정할 수 없다. 대신 아래 관리자 확인에서 근거가 부족하면 보류한다.

**관리자 확인** (아래 근거가 모두 갖춰지지 않으면 **보류**)

1. 플레이어 신고(시각, 상품, 수량)를 받는다.
2. **장애 시점 근거**: 위의 장애 추정 시각이 있고, 서버 로그(`docker logs`)에도 정상 종료 메시지 없이 끊긴 흔적이 있다.
3. **유실 시간대 근거**: 정상 종료 기록이 없으면 마지막 heartbeat는 서버가 살아 있던 마지막 확인 시각이다. 같은 기동에서 heartbeat 뒤에 커밋된 출금도 조사한다. heartbeat 이전 구매는 운영 서버의 실제 플레이어 저장 간격(`config/paper-global.yml`의 `player-auto-save-rate`와 월드 자동 저장 간격 중 짧은 쪽) 안에 있는지 확인한다. 그보다 이전 구매는 인벤토리가 이미 저장됐을 가능성이 높으므로 보류. 그 플레이어가 구매 뒤 장애 전에 접속을 끊었다면(로그아웃 때 저장됨) 역시 보류.
4. **금액 근거**: 신고한 상품의 6.3 가격 × 수량이 거래 금액과 정확히 같다. 후보가 여러 건이면 `context`(상점 창 제목, 위치)로 좁히고, **그래도 한 건으로 특정되지 않으면 보류.**
5. **상품 부재 근거**: 플레이어 인벤토리·엔더 상자에 그 상품이 없다. 단, 이것만으로는 "지급 후 소비"와 구별되지 않으므로 2–4번 없이 이것만으로 환불하지 않는다. EconomyShopGUI 로그는 참고만 한다(로그도 함께 날아갔을 수 있음).
6. 환불만 하고 상품은 다시 주지 않는다. 환불·보류 결정과 근거를 노션에 한 줄 기록.

보류된 건은 그 금액이 소액(MVP 기준 2,000원 이하, 직업 약 12분치)이면 관리자 판단으로 `/bank give`로 보상하고 기록한다. 그보다 크면 같은 시점의 CoreProtect 기록 등 다른 근거가 나올 때까지 보류한다.

## 3. 시스템 구성

```
플레이어
  ├─ /jobs ...        → VJobs            (돈 공급: 직업 보상)
  ├─ /shop            → EconomyShopGUI   (돈 소비: 구매)
  ├─ /money, /pay, /baltop → Bank (자체) (잔액·송금·순위)
  └─ /economy (1.5단계) → EconomyHub (자체) : 위 명령을 GUI 버튼으로 묶음
                 │
        VaultUnlocked (공통 경제 API)
                 │
        Bank (자체, 경제 제공자)  → plugins/Bank/bank.db (백업 대상)
```

- 잔액은 Bank 한 곳에만 저장한다. 다른 자체 플러그인(EconomyHub, Trade)도 Bank를 직접 부르지 않고 VaultUnlocked API로 조회·입출금한다.
- VJobs 직업 데이터는 VJobs의 SQLite, 상점 가격은 EconomyShopGUI 설정 파일. 둘 다 `plugins/` 아래라 `backup.sh`에 이미 포함된다.

### 4.1 경제 기준값

**"직업 활동에 집중한 1시간 ≈ 10,000원"**을 기준으로 삼는다.

### 5.3 레벨 경험치

- 보상 10원당 경험치 1 → 직업 1시간 ≈ 1,000 XP.
- 레벨 n → n+1 필요 경험치 = `440 × n^0.6` (Lv1→2: 440, Lv10→11: 1,752, Lv30→31: 3,386, Lv49→50: 4,545)
- 누적 소요 시간(Lv1 시작, 직업 1개에 시간당 10,000원 기준):

| 도달 레벨 | 10 | 20 | 30 | 40 | 50 |
| --- | --- | --- | --- | --- | --- |
| 누적 시간 | 10.0h | 31.8h | 61.7h | 98.5h | 141.4h |

- v0.3의 `100 × n^1.5`는 실제로 Lv30 189시간, Lv50 690시간이 걸려 목표와 맞지 않아 교체했다.
- VJobs의 곡선 설정 형식이 이 식을 그대로 못 받으면, 표의 누적 시간에 맞도록 근사한다. 레벨은 MVP에서 보너스가 없어 자랑거리 정도의 의미. 2.5단계부터 15장 편의 스킬 해금 조건(Lv.10·20·30·50)으로 연결된다(수입 보너스는 계속 0%).

## 6. 서버 상점 (EconomyShopGUI)

### 6.1 차익(무한 수익) 방지 규칙

MVP는 서버 매입(플레이어가 서버에 파는 것)이 없어서 차익이 생길 수 없다. 아래 규칙은 **나중에 매입을 추가할 때** 반드시 지킨다.

1. **매입 가격 ≤ 구매 가격의 25%** (같은 아이템).
2. **조합 차익 금지**: 재료를 사서 만든 결과물의 매입가 ≤ 재료 구매가 합. 반대로 결과물을 사서 분해한 재료의 매입가 합 ≤ 결과물 구매가. (예: 철 블록 ↔ 철 주괴 9개)
3. **제련 차익 금지**: 원석·광석 매입가 ≤ 결과물 매입가가 되지 않게.
4. **자동 생산 가능 자원은 매입하지 않음**: 조약돌·돌·현무암·얼음·모래(가루기)·사탕수수·대나무·호박·수박·켈프·밀·당근·감자·썩은 살점·뼈·실·화약·철(골렘 농장)·금(피글린 농장)·양털·꿀·에메랄드(주민)·청금석·레드스톤(성직자 주민) 등.
5. **주민 거래가와 비교**: 주민에게 싸게 사서 상점에 팔 수 있는 아이템은 매입하지 않는다.

이 규칙을 적용하면 매입 후보는 다이아몬드 같은 재생 불가 자원 정도만 남는다. 돈 공급은 직업 보상이 담당한다.

### 6.2 판매 제외 (돈으로 못 사는 것)

**EconomyShopGUI(`/shop`)에서는** 아래 전부를 팔지 않는다. 이 중 다이아몬드·에메랄드·인챈트 책·경험치 병·황금 사과·엔더 진주는 v0.8부터 **자체 `Market`에서 주간 한도를 걸고** 판다(13장). EconomyShopGUI 무료판은 플레이어별 구매 한도(`stock-limit-player`)가 프리미엄 기능이라 한도를 걸 수 없기 때문이다.

다이아몬드·에메랄드·네더라이트(관련 전부), 다이아·네더라이트 장비, 인챈트 책, 경험치 병, 황금 사과·마법이 부여된 황금 사과, 불사의 토템, 겉날개, 셜커 상자·껍데기, 스포너·스폰 알, 네더의 별·신호기, 트라이던트, 철갑 껍데기, 엔더 진주·엔더의 눈, 커스텀 고성능 장비.

**어디서도 팔지 않는 것**(v0.8에도 유지): 네더라이트 관련 전부(고대 잔해·파편·주괴·강화 대장장이 형판), 다이아·네더라이트 장비 완제품, 마법이 부여된 황금 사과, 불사의 토템, 겉날개, 셜커 상자·껍데기, 스포너·스폰 알, 네더의 별·신호기, 트라이던트, 철갑 껍데기, 엔더의 눈, 커스텀 고성능 장비, 저주 인첸트.

### 7.2 `/economy` (EconomyHub) 상세

- 의존: `compileOnly` Vault API, `plugin.yml`에 `softdepend: [VJobs, Vault]`. Vault는 잔액 표시에만 쓰므로 `depend`로 두지 않는다(Vault가 없어도 1b 직업 보호 기능은 계속 돌아야 함). 다른 버튼의 플러그인(EconomyShopGUI·Bank·Market·Trade)은 누를 때 켜져 있는지만 본다
- 메뉴 두 개(1.5단계, 확정 레이아웃은 7.4): `/economy`(`/경제`) 9×3 허브, `/직업` 9×5 직업 관리. 명령·안내 문구·직업 목록·보상 요약 키는 `config.yml`의 `menus`, 슬롯 배치는 코드
- 외부 플러그인은 명령 또는 **공개 API를 리플렉션으로** 부른다(VJobs는 공개 Maven 저장소가 없음). 이름이 바뀌면 그 기능만 꺼지고 로그에 남는다. `/직업`은 VJobs 2.2.0 공개 API `VJobsApi.joinJob(Player, id)`(결과 `SUCCESS`·`UNKNOWN_JOB`·`ALREADY_JOINED`·`LIMIT_REACHED`·`COOLDOWN`·`CANCELLED`, JAR 확인)·`leaveJob(Player, id)`·`getPlayer(uuid).getJobs()`를 쓴다. API로 가입·탈퇴해도 VJobs가 `JobJoinEvent`·`JobLeaveEvent`를 내므로 아래 쿨타임 면제·XP 유지가 그대로 적용된다(로컬 테스트 서버에서 확인할 것). 이 두 이벤트 연결에 실패한 기동에서는 `/직업`을 열지 않는다(탈퇴 시각·XP 기록 없이 탈퇴시키지 않음)
- `/직업`의 쿨타임 남은 시간은 아래 직업 쿨타임 면제와 같은 값(`job-leaves.tsv`와 PDC 중 늦은 탈퇴 시각 + VJobs `job-switch-cooldown.default-seconds`). 가입 안 한 직업의 레벨은 VJobs 보관 진행도(`getArchivedProgress`, 내부 호출, 없으면 Lv.1, 읽지 못하면 레벨 표시 생략). 보상 요약은 VJobs `config.yml`의 `jobs.<id>.actions.<action>.<key>.money`를 읽어 표시(값을 두 곳에 두지 않음)
- **1b에 먼저 배포하는 직업 보호 기능** (GUI보다 먼저, VJobs API는 리플렉션으로 호출해 VJobs JAR 없이 컴파일)
- **직업 쿨타임 면제** (5.1): `JobLeaveEvent`(MONITOR, ignoreCancelled)에서 탈퇴 시각을 `plugins/EconomyHub/job-leaves.tsv`(fsync, 30일 지난 줄은 정리)와 플레이어 PDC(`economyhub:last_job_leave`)에 저장하고 늦은 쪽을 쓴다. PDC만 쓰면 VJobs가 탈퇴를 DB에 저장한 뒤 강제 종료됐을 때 탈퇴 시각만 사라져 쿨타임이 풀린다(최종 점검). 파일을 읽지 못한 기동에서는 아무에게도 면제를 주지 않는다(VJobs 기본 쿨타임). 접속·탈퇴·30초 주기로 확인해, 마지막 탈퇴 후 쿨타임이 지났거나 탈퇴 기록이 없으면 `PermissionAttachment`로 `jobs.cooldown.instant=true`, 쿨타임 안이면 떼어 냄. VJobs 쿨타임은 `jobs.cooldown.instant`가 있으면 0초. **쿨타임 길이는 VJobs `config.yml`의 `job-switch-cooldown.default-seconds` 한 곳에서만 정한다**(2차 리뷰 반영). EconomyHub는 확인할 때마다 이 값을 읽고 자기 설정에 따로 두지 않아서, 두 값이 어긋나 짧은 쪽이 적용되는 일이 없다. 테스트: 첫 직업 → 바로 두 번째 가입 성공, 하나 탈퇴 → 1시간 안 재가입 거부 → 1시간 뒤 성공, 재접속·재시작 후에도 유지
- **탈퇴 후 XP 유지** (5.1). VJobs는 데이터를 메모리에 두고 5분 자동 저장·접속 종료·서버 종료 때만 SQLite에 쓴다(JAR 확인). 플레이어 PDC는 Paper가 따로 저장해서 저장 순서가 엇갈리면 복구 기록만 먼저 지워질 수 있다(리뷰 6차: 복구 직후 강제 종료 → Lv3 유지, XP 0). 그래서:
  - 기록은 `plugins/EconomyHub/job-xp.tsv`(uuid, 직업, `레벨:XP[:r]`). 바꿀 때마다 임시 파일 → fsync → 바꿔치기. 기동 때 파일을 읽지 못하면 파일을 보존하고 XP 유지가 적용되는 직업의 탈퇴를 취소한다(리뷰 7차). 현재 XP가 0이어도 파일에 복구 대기 기록이 있는지 확인할 수 없다
  - `JobLeaveEvent`(HIGHEST, 탈퇴 직전): `VJobsApi.getPlayer(uuid).getJob(id)`의 레벨·XP를 기록. 기존 기록이 지금보다 앞서 있으면(더 높은 레벨, 또는 같은 레벨에 더 큰 XP) 그 값을 유지(재접속 직후 복구 전에 다시 탈퇴해도 유실 없음, 리뷰 7차). 쓰기에 실패하면 탈퇴를 취소
  - 복구는 두 순간에만, 그 순간의 VJobs 값 기준으로 한 번: 재가입(`JobJoinEvent` MONITOR, 기준은 그 시점 VJobs 보관 진행도 `getArchivedProgress`, 없으면 Lv1·XP 0. VJobs `join()`이 이벤트 직후 이 값으로 가입시킴, JAR 확인) → 계산해 둔 양을 다음 틱에 지급해 가입한 틱에 얻은 XP도 흡수하지 않음(재검증: 가입 틱에 다이아 40 → 163.5). 다음 틱 전에 같은 틱에 다시 탈퇴하면 탈퇴 기록 전에, 퇴장하면 `PlayerQuitEvent`(LOWEST, VJobs 퇴장 저장 전)에 예정된 복구를 먼저 반영(재검증: 가입 틱 채굴 직후 탈퇴 → 기록 163.5). 그리고 접속 후 VJobs가 데이터를 다 읽은 첫 틱(`VJobsApi.getPlayer` 가 생기는 틱, 최대 30초 기다림). 기록의 레벨·XP까지 모자란 만큼 `giveXp`(배율 없음). 레벨이 더 낮으면(강제 종료로 VJobs DB가 예전 상태) 그 사이 레벨업분 `xpForLevel(n+1)`까지 더해 한 번에 줌(VJobs `applyLevelUps`가 `xp ≥ xpForLevel(level+1)`이면 빼고 레벨업, JAR 확인). 기록은 지우지 않고 `:r`(복구함)로만 바꿈. 그 뒤 새로 얻은 XP는 계산에 들어가지 않아 흡수되지 않음(최종 점검: 123.5 보관 + 새 채굴 40 → 163.5). 레벨이 낮다는 이유만으로 기록을 지우지 않음(최종 점검)
  - 1분마다 비동기로 VJobs DB(`JobManager.getRepository().load(uuid)`, 내부 클래스)를 읽어 같은 레벨에 저장 XP 이상(또는 더 높은 레벨)인 `:r` 기록만 삭제. VJobs 저장 전에 서버가 꺼지면 기록이 남아 재접속 후 모자란 만큼 다시 준다
  - VJobs가 실제로 쓰는 탈퇴 설정(`ConfigManager.getLeavePenaltyPercent()`, `isLeaveKeepArchive()`)을 탈퇴·재가입·복구 직전마다 확인. 벌칙이 0이 아니거나 `keep-progress`가 꺼져 있으면 저장·복구하지 않고, 그 상태로 재가입하면 남은 기록을 버린다. 설정을 읽지 못하면 기록만 저장하고 복구·삭제는 하지 않는다. VJobs DB를 읽을 수 없으면 기록 정리만 끔(복구는 모자란 만큼이라 그대로 안전). 시작 로그와 `/economyhub status`에 실제 상태(`켜짐 (기록 n건)` / `꺼짐 (VJobs 탈퇴 벌칙 10.0%)`)
  - 테스트: Lv3 + XP 123.5 → 탈퇴 → 재가입 → 123.5. 복구 직후 강제 종료 → 재기동·접속 → 123.5 다시 복구(로그 `(VJobs 저장 전 종료 후 다시)`). 복구가 돌기 전에 다시 탈퇴해도 123.5 유지. 기록 Lv3·XP 34 + DB Lv2 상태로 강제 종료 → 접속 → Lv3·XP 34(로그 `(Lv2 에서)`). 강제 종료 후 접속 → 복구 → 바로 40 채굴 → 163.5. VJobs가 탈퇴를 저장한 뒤 강제 종료 → 재기동 후에도 1시간 쿨타임. 자동 저장 뒤 강제 종료 → 재접속 때 추가 지급 없음. 손상된 기록 파일로 시작하면 XP 유지 정책에서 탈퇴 취소. 벌칙 0% 탈퇴 → 10%로 바꾸고 `/vjobs admin reload` → 재가입 → 복구 안 됨
- **피스톤 이동·유체 생성 블록 보상 제외** (8장): VJobs 2.2.0의 설치 블록 기록은 좌표 기준이고 피스톤 이벤트를 처리하지 않아(JAR 확인), 설치한 원목·광석·호박을 피스톤으로 밀면 자연 블록으로 보고 다시 지급한다(원목 설치 → 밀기 → 베기 반복으로 무한 수입). 돌 생성기(용암 + 물)로 만든 돌도 설치 기록이 없어 1원씩 지급된다. EconomyHub가 `BlockPistonExtendEvent`/`RetractEvent`로 움직인 블록의 도착 좌표(이벤트 방향으로 한 칸, 끈끈이 피스톤이 당길 때도 실제로 움직인 블록의 도착 좌표만)와 `BlockFormEvent`로 생긴 돌·조약돌·현무암 등의 좌표를 청크 PDC에 표시해 두고, 표시된 블록을 캘 때 `JobPayoutEvent`(BREAK·HARVEST)를 취소한다. 표시는 그 블록을 캐면 지운다. 저장은 청크 구역(16×16×16)마다 4,096비트 비트맵(`economyhub:u<구역 y>`, `long[64]`)이라 개수 상한이 없고, 실제로 남아 있는 표시를 모두 보존한다(2차 리뷰 반영: 개수 상한을 넘으면 오래된 표시부터 지우던 방식은 남아 있는 블록을 다시 보상 대상으로 만들었음). Market(14.2)도 같은 표시를 읽어 판매 가능량에서 뺀다
- 아이템 이동 차단: 7.4 공통 규칙 (NeatSort 등 정렬 플러그인과 충돌 방지 위해 `InventoryHolder` 커스텀 홀더로 식별)

### 7.3 `/trade` 요구사항 (2단계)

- 접속자 목록 GUI(기존 `/tpa` GUI 재사용) → 요청 → 30초 내 수락

- 돈은 확정 순간에만 출금·입금(잔액 부족 시 거래 취소). 모든 거래는 로그 파일에 기록
- **구현 설계는 [TRADE.md](TRADE.md)** (2026-11-27 확정: 금액 입력 Paper 대화창, 바닐라 아이템 전부 허용, 수수료·한도 없음, 같은 상대 10초 재요청 금지, Bank 없으면 거래 잠금, 로그는 하루 단위 파일, **제시 방식 — 아이템은 정산 순간까지 인벤토리에 그대로**). 아래 ①–④는 TRADE.md 3–5장·2장에서 정함.
- 정할 것이었던 항목 (2026-11-25 범위 정리): ① 거래 칸에 넣은 아이템은 플레이어 파일에서 빠져 메모리에만 있으므로, 강제 종료 대비로 거래 칸 내용을 디스크에 기록(저널)하고 기동 때 원래 주인에게 돌려줘야 함. ② 양쪽 돈 이동을 Vault 출금·입금 두 번으로 하면 중간 실패가 생기므로 Bank Java API의 한 트랜잭션 이체(extRef)를 씀(3장 "Vault로만"의 예외, Market과 같음). ③ 금액 입력은 모루 GUI 또는 채팅 입력 중 하나(표지판은 실제 블록이 필요). ④ `TpaMenu`는 Travel 플러그인 안에 있으므로 `common`으로 옮기거나 구조를 복사, 전투 태그 확인은 `softdepend: [Travel]` + Travel 쪽 작은 공개 API

### 7.4 자체 GUI 확정 레이아웃 (2026-11-25)

자체 개발 플러그인(`EconomyHub`, `Market`, `Trade`)의 GUI는 아래 레이아웃과 바닐라 아이템 규격으로 구현한다. 1.5단계는 7.4.1–7.4.2(EconomyHub), 1.7단계는 7.4.3–7.4.5(Market), 2단계는 7.4.6(Trade). 슬롯 번호는 0부터.

**공통 규칙** (`common` 모듈 `kr.commata.common.gui`: `Menu`, `MenuListener`, `Items`, `ClickLock`. 플러그인마다 `MenuListener`를 하나 등록)

- 모든 자체 GUI는 전용 `InventoryHolder`로 식별해 클릭·드래그·숫자키·`F`·Shift 클릭·더블클릭 모으기·크리에이티브 복제·아래 인벤토리 클릭을 모두 취소한다(`Trade` 본인 4×4 칸만 예외, 7.4.6). 플러그인을 끌 때 열린 메뉴를 먼저 닫는다
- 빈칸 채움은 `GRAY_STAINED_GLASS_PANE`(이름 `" "`), 닫기 버튼은 우측 하단 `BARRIER`. 이름·로어는 MiniMessage(기울임 없음), 도구 아이콘의 공격력 줄은 숨김
- 거래 성공 시 창을 닫지 않고 슬롯(잔액·한도·천장·판매 가능량)만 제자리 갱신. 제목에 숫자가 있는 창(`/직업`, `/희귀상점`)은 제목만 바꿔 보냄. 연타 방지 클릭 락 250ms(플레이어별). 락은 체감용이고 중복 처리는 각 기능의 "플레이어당 거래 하나" 규칙이 막는다
- 창을 닫거나 다른 명령을 실행하는 버튼은 클릭 이벤트 안에서 바로 하지 않고 다음 틱에 처리
- 버튼은 **일반 좌클릭·우클릭에서만** 동작한다(`MenuListener`가 그 밖의 클릭을 버튼에 전달하지 않음, v0.9.1). 숫자키·`F`·`Q`·Shift 클릭·더블클릭은 취소만 한다. 예외(v0.9.4): 메뉴가 칸별로 허용한 경우에만 **Shift+좌클릭**도 버튼에 전달한다(지금은 `/판매` 품목 칸만, 7.4.5). 이때도 아이템 이동 자체는 그대로 취소한다. `Trade` 본인 칸(7.4.6)은 이 규칙 밖에서 직접 처리

- 1줄(직업 탭): `2` 광부(`IRON_PICKAXE`), `3` 벌목꾼(`IRON_AXE`), `4` 농부(`IRON_HOE`), `5` 사냥꾼(`IRON_SWORD`), `6` 낚시꾼(`FISHING_ROD`). 내 직업 2개는 다이아 도구(낚시꾼은 광택) + 직업별 실제 보너스(`<#55FF55>[직업 보너스 +150% 적용 중]`처럼 낚시꾼 +150%, 벌목꾼 +200%, 나머지 +100%, 14.4), 선택된 탭은 `<#55FFFF>[현재 탭]`
- 2–4줄(품목): `10–16`, `19–25`, `28–34` 21칸. 벌목꾼은 원목·줄기 11종만(껍질 벗긴 원목·나무 블록 제외)으로 21칸 안에 들어감. 로어(14.3): 판매 단위(`1개`/`2개`/`16개`), 단가(`기본 X원`, 내 직업이면 `기본 X원 → 보너스 Y원`), `보유 수량`, `보너스 판매 가능(job_amount)`, `기본 판매 가능(base_amount)`, `오늘 남은 한도: N원`, 클릭 안내 3줄 + 보조 1줄(2026-11-26 사용자 요청으로 문구 명확화): `▶ 좌클릭: <단위>개씩 판매 (지금 N개 · +M원)`, `▶ Shift+좌클릭: 최대 <한 칸>개 판매 (지금 N개 · +M원)`, `▶ 우클릭: 팔 수 있는 만큼 전부 판매 (지금 N개 · +M원)`, `(보유 수량·판매 가능량·오늘 남은 한도 안에서)`. N·M은 그 클릭을 지금 했을 때 실제로 팔리는 양과 금액. Shift+좌클릭은 판매 단위의 배수로, 그 품목의 한 칸 최대치(대부분 64개, 엔더 진주 16개)와 보유 수량 중 작은 쪽까지 판다(판매 가능량·일일 한도는 다른 클릭과 같이 적용, 2026-11-26 사용자 결정)
- 5줄(일일 한도 게이지 `37–43` 7칸): 사용 칸 수 = `floor(오늘 판매액 × 7 ÷ 5,000)` 만큼 `LIME_STAINED_GLASS_PANE`, 나머지 `LIGHT_GRAY_STAINED_GLASS_PANE`, 100%면 `RED_STAINED_GLASS_PANE` 7칸. 로어 `오늘 판매액: X / 5,000원`
- 6줄: `45` 메인 허브(`OAK_DOOR` → `/economy`, EconomyHub가 꺼져 있으면 빈칸), `46` 내 잔액, `49` 일일 초기화 안내(`CLOCK`, 매일 00:00 KST), `53` 닫기 (2026-11-26 메인 허브 추가, 잔액 45→46)
- **처리 중 표시**: 저장 확인 대기(구매 `CHARGED`, 판매 `PENDING`, 13.6·14.3)로 그 플레이어의 Market이 잠기면 거래 버튼을 모두 `GRAY_DYE` + `처리 중(저장 확인 대기)`로 바꾸고, 받지 못한 구매품은 `/market claim` 안내

#### 7.4.6 `Trade` — `/trade` 1:1 교환 창 (9×6, 2단계)

- 제목 `<#F5C542>1:1 안전 거래` (고정. 카운트다운은 슬롯 `22`로만 표시: 제목을 매초 바꾸면 창을 다시 보내 커서 아이템·드래그가 끊길 수 있음)
- 좌측 4×4 `0–3, 9–12, 18–21, 27–30`: **내 제시 칸**(표시 전용, 2026-11-27 제시 방식). 아래 내 인벤토리 칸을 **좌클릭 = 그 칸 전부 제시, 우클릭 = 1개 추가**하면 빈 제시 칸에 그 아이템(제시 개수)이 보인다. 제시 칸 **좌클릭 = 빼기, 우클릭 = 1개 빼기**. 로어 `<#AAAAAA>내 인벤토리 <n>번 칸 · 제시 <x>/<보유>` + `<#55FF55>▶ 좌클릭: 빼기 / 우클릭: 1개 빼기`. **아이템은 정산 순간까지 인벤토리에서 움직이지 않음**([TRADE.md](TRADE.md) 0·3장). 우측 4×4 `5–8, 14–17, 23–26, 32–35`: 상대 제시 칸(읽기 전용, 실시간 표시)
- 중앙 열: `4` 내 제시 금액(`OAK_SIGN`, `<#FFDF6B>내 제시 금액: X원`, 클릭 시 금액 입력), `13` 상대 제시 금액(`GOLD_INGOT`, 읽기 전용), `22` 카운트다운(대기 `GRAY_STAINED_GLASS_PANE`, 확정 중 `CLOCK` 개수 3 → 2 → 1), `31` 구분선, `40` 내 확인 토글(`RED_CONCRETE` `준비 대기 (클릭하여 확인)` ↔ `LIME_CONCRETE` `준비 완료`), `49` 거래 취소(`BARRIER`, 즉시 취소·반환)
- 5줄 상태 바: `36–39` 내 준비 상태 유리판(빨강/연두), `41–44` 상대 준비 상태
- 6줄: `45` 내 정보(`PLAYER_HEAD`, 내 잔액), `53` 상대 정보(`PLAYER_HEAD`, 닉네임·준비 상태)
- 위·아래 인벤토리의 **모든 클릭·드래그를 취소**하고 해석만 한다(다른 자체 GUI와 같은 차단, 예외 창이 아님). 해석하는 것: 아래 인벤토리 좌·우클릭(제시 추가), 위 내 제시 칸 좌·우클릭(빼기), `4` 금액, `40` 준비, `49` 취소. Shift·숫자키·`F`·`Q`·더블클릭·드래그·크리에이티브 중클릭·꾸러미 우클릭은 아무 동작 없음. 아래 인벤토리에서 이미 제시한 칸을 다시 좌클릭하면 그 칸 전부로 맞추고, 칸 내용이 바뀌면(줍기 등) 그 제시는 지워지고 양쪽 준비 해제
- 아이템·금액이 바뀌면 양쪽 확인 즉시 해제. 크리에이티브·관전 모드에서는 요청·수락 불가. 접속자 선택 창은 Travel의 `/tpa` GUI(`TpaMenu`) 구조를 재사용(7.3)

**7.4.6a 추가 화면 (2026-11-27 사용자 확정)**

- **접속자 선택 `/trade` (9×6)**: 제목 `<#F5C542>거래할 플레이어 선택`. `0–44` 다른 접속자 머리(`PLAYER_HEAD`, 이름 `#55FFFF`, 로어 `▶ 클릭하여 거래 요청`). 요청할 수 없으면 이름 회색 + 이유 한 줄(`거래 중`, `전투 중`, `요청 대기 n초`, `재요청 n초 뒤`). `45` 이전 쪽(`ARROW`), `48` 메인 허브(`OAK_DOOR` → `/economy`), `49` 안내(`BOOK`: 요청 30초 안에 수락, 거리 제한 없음, 전투 중 불가), `50` 다음 쪽(`ARROW`), `53` 닫기(`BARRIER`). 보낸 요청이 있으면 `49` 대신 `CLOCK` `보낸 요청: <닉> (n초 남음)` + `▶ 클릭하여 요청 취소`. 아무도 없으면 `22` `GRAY_STAINED_GLASS_PANE` `다른 접속자가 없습니다`.
- **요청 받기 (채팅)**: 받는 사람에게 `<#F5C542>[거래] <닉>님이 거래를 요청했습니다 (30초)` + 클릭 버튼 `<#55FF55>[수락]`(`/trade accept <닉>`) `<#FF5555>[거절]`(`/trade deny <닉>`) + 알림음 1회. 보낸 사람에게 `요청을 보냈습니다`. 만료·거절·수락은 양쪽 채팅 안내.
- **금액 입력 (Paper 대화창)**: 거래 창 `4`번 클릭 → 대화창 제목 `<#F5C542>제시 금액 입력`, 본문 `내 잔액: X원` · `0을 입력하면 금액 없이 거래합니다`, 텍스트 입력 1칸(라벨 `금액 (원)`, 최대 13자, 현재 제시 금액이 기본값), 버튼 `<#55FF55>확인` / `<#AAAAAA>취소`. 확인 → 정수·0 이상·잔액 이하이면 반영(양쪽 준비 해제), 아니면 채팅 `<#FF5555>금액은 0 이상 정수, 잔액 이하만 가능합니다` 후 거래 창으로 돌아감. 대화창이 떠 있는 동안 본인 준비는 자동 해제, 상대 화면 `4`·`13`은 `입력 중…` 표시.
- **완료·취소 안내 (채팅)**: 완료 `<#55FF55>[거래] 완료: 받은 것 …, 보낸 것 …`. 취소 `<#FF5555>[거래] 취소됨 (<사유>)` (아이템은 움직이지 않았으므로 반환 안내 없음). 정산 뒤 인벤토리가 모자라 남은 받을 물건이 있으면(복구 때만 생김) `/trade claim` 안내.

## 9. 배포 절차

Bank는 다른 자체 플러그인처럼 `deploy.ps1 -Plugin bank`로, 외부 플러그인도 같은 `scripts/server/install-plugin.sh`로 설치한다. 이 스크립트는 JAR 안의 `plugin.yml` 이름을 읽어 처리하므로 우리 JAR이 아니어도 되고, 백업 → 정지 → 교체 → 시작 → 로드 확인 → 롤백 기록까지 그대로 쓸 수 있다. Chunky·CoreProtect 보호도 그대로 유지된다.

### 9.1 테스트 (로컬)

1. `.\gradlew :plugins:bank:runServer`로 뜨는 테스트 서버(`plugins/bank/run/`)의 `plugins/`에 9.3에 고정한 외부 JAR 4개(VaultUnlocked·VJobs·EconomyShopGUI·LuckPerms)를 넣고 실행 → 설정 파일 생성
2. 5·6장 값으로 설정을 고치고 재시작, 6.4의 LuckPerms 명령 실행 → 2.1 첫 연동 테스트부터 진행
3. 8장 체크리스트 + 2.1 체크리스트 진행 (TestBot 계정 포함 2인). 벌목꾼은 실제 수동 벌목량(목표 8,000원 = 원목 1,000개/시간, 일반 나무와 **2×2 가문비 + 뼛가루** 두 가지 기준, 1,500개 초과 시 5.2 기준대로 보상 하향)과 **직업 2개 겸업 시 합산 수입**을 따로 잰다
4. Travel·Pets·CustomItems와 함께 켜서 로드 오류 없는지 확인
5. 통과한 설정 폴더 전체(`plugins/VJobs/`, `plugins/EconomyShopGUI/`, `plugins/LuckPerms/`의 설정 파일, 데이터 파일 제외)를 레포 `server-config/economy/`에 커밋

### 9.2 운영

```powershell
# Windows: 1) Bank 먼저 업로드만 (설치는 외부 플러그인과 한 번에)
.\scripts\deploy.ps1 -Plugin bank -SshHost minipc-lan -UploadOnly
.\scripts\deploy.ps1 -Plugin economy-hub -SshHost minipc-lan -UploadOnly   # 직업 보호 기능 (7.2)
# 2) 외부 JAR 업로드
ssh minipc-lan "mkdir -p ~/plugin-staging/economy"
scp .\external\*.jar minipc-lan:~/plugin-staging/economy/
```
```bash
# 미니PC
~/mc-scripts/install-plugin.sh --dry-run ~/plugin-staging/bank-*.jar ~/plugin-staging/economy-hub-*.jar ~/plugin-staging/economy/*.jar   # 새 플러그인 6개만 나오는지 확인
~/mc-scripts/install-plugin.sh ~/plugin-staging/bank-*.jar ~/plugin-staging/economy-hub-*.jar ~/plugin-staging/economy/*.jar   # 백업 + 설치 + 재시작
```

**운영 첫 기동부터 검증된 설정으로 뜨게 한다.** 기본 설정으로 한 번 열면 그 사이 접속한 사람이 기본 상품을 팔 수 있다.

1. 위 업로드와 함께 `server-config/economy/`를 미니PC `~/plugin-staging/economy-config/`로 올린다.
2. `install-plugin.sh` 실행 **전에**(서버가 켜져 있어도 됨, 아직 로드 안 된 플러그인 폴더라 서버가 건드리지 않음) 설정을 `plugins/` 아래 각 폴더로 복사하고, 소유자를 기존 `plugins/` 폴더와 같게 맞춘다.
   ```bash
   cp -r ~/plugin-staging/economy-config/. /home/deploy/services/minecraft/data/plugins/
   ```

**오픈 전 접속 제한.** `-Delay 0`은 재시작 공지 대기만 생략할 뿐 접속을 막지 않는다. 설치부터 검증까지는 접속을 따로 막는다.

- 미리 디스코드 등으로 "점검 중 접속 금지"를 공지한다. **OP 계정은 화이트리스트를 무시하고 들어올 수 있으므로** 공지가 실제 차단 수단이다.
- 비OP 계정은 화이트리스트를 임시로 줄여서 막는다. 서버 콘솔에서 `whitelist list`로 명단을 기록해 두고, 관리자 본인만 남긴 뒤(`whitelist remove <닉>`) 9.2의 7번에서 다시 추가한다. itzg 이미지가 `WHITELIST` 환경 변수로 명단을 관리하고 있다면 재시작 때 원래 명단으로 덮어쓸 수 있으니, 3번 재시작 직후 `whitelist list`로 다시 확인한다.

3. `install-plugin.sh`로 설치·재시작. 첫 기동이 곧 최종 설정이다. Bank는 이때 빈 DB를 만든다(2.3).
4. LuckPerms 권한은 설정 파일이 아니라 LuckPerms DB(기본 H2)에 저장되고, 이 DB는 테스트 서버에서 복사해 오지 않는다. 첫 기동 직후 서버 콘솔에서 다음을 실행한다. 이 몇 분 동안에도 1겹(`shops.yml`에 판매가 없음)이 이미 적용돼 있어 팔 수 있는 상품은 없다.
   ```
   lp group default permission set jobs.limit.2 true
   lp group default permission set EconomyShopGUI.sellall false
   lp group default permission set EconomyShopGUI.sellallitem false
   lp group default permission set EconomyShopGUI.sellallhand false
   lp group default permission set EconomyShopGUI.sellgui false
   ```
5. 일반 권한으로 검증한다. 관리자 계정을 잠시 `deop <닉>` 하고 진행한 뒤 콘솔에서 `op <닉>`으로 되돌린다(운영 서버는 정품 인증이라 TestBot 계정은 못 씀).
   - 직업 두 번째 가입 성공, 세 번째 가입 거부
   - 6.4 판매 검증 4가지(아이템·잔액 그대로)
   - 2.1 첫 연동 테스트(직업 보상 → 구매 → `/money` 차액)
6. **기준 백업**: 서버를 멈추고 `backup.sh --offline`으로 정지 상태 백업을 남긴 뒤 다시 켠다(`bank.db`와 권한이 들어간 첫 백업, 2.3).
   ```bash
   docker stop -t 90 minecraft-paper && ~/mc-scripts/backup.sh --offline && docker start minecraft-paper
   ```
7. 화이트리스트 명단을 원래대로 되돌리고(`whitelist add <닉>`) 오픈 공지를 한다.

- 설정 복사는 `/reload` 없이 재시작으로 반영(기존 원칙 유지).
- 되돌리기: `~/mc-scripts/rollback.sh`는 JAR만 원복하고 잔액은 그대로다. 잔액을 과거로 돌려야 하면 Bank 폴더만이 아니라 같은 시점의 전체 백업을 복원한다(2.3).
- 오픈 공지: 노션에 명령어표(`/jobs`, `/shop`, `/money`, `/pay`, `/baltop`, 이후 `/economy`).

### 9.3 설정 파일 관리

## 13. 희귀 상점과 인첸트 책 뽑기 (v0.8 기획 변경)

> 상태: **확정**(2026-11-25, 13.8). 다음은 `plugins/market` 개발.

### 13.1 왜 바꾸나

- 유저들이 순수 야생보다 **돈을 모아서 쓰는 콘텐츠**를 더 원한다.
- v0.7까지는 돈을 쓸 곳이 건축 블록·음식 정도라, 직업을 꾸준히 하는 사람은 잔액만 쌓인다(소비처 부족 → 돈의 가치 하락). 희귀품과 뽑기는 **강한 소비처**라 쌓이는 돈을 흡수한다.
- 돈이 생기는 곳은 직업 보상과, 14장의 직업별 매입(직접 얻은 것만)뿐이다. 상점·희귀 상점에서 산 물건은 매입 대상이 아니므로(14.2) 희귀품을 팔아도 "사서 되팔아 돈 복사" 같은 순환은 생기지 않는다.

### 13.2 경제 밸런스 영향

기준: 직업 1시간 ≈ 10,000원(4.1), 하루 2시간 하는 사람 ≈ 하루 20,000원, 주 140,000원.

| 영향 | 판단 | 대응 |
| --- | --- | --- |
| 통화량 | 소비가 크게 늘어남 → 인플레이션 억제. 14장 매입이 공급을 직업별로 시간당 15–50% 늘리지만(하루 5,000원 한도) 희귀 상점·뽑기 소비가 더 큼 | 10장에 희귀 상점·뽑기 지표 추가 |
| 다이아 가치 | 상점가가 생기면 플레이어 간 거래가의 **상한**이 된다(그 이상 주고 살 사람이 없음) | 상점가를 "직접 캐는 것"보다 비싸게 + 주간 한도 |
| 광부 직업 | 광부 1시간 = 다이아 약 8개 + 8,800원. 같은 1시간 다른 직업 10,000원으로는 다이아 6개(1,500원 기준)밖에 못 삼 → **직접 캐는 쪽이 계속 이득** | 다이아 가격은 1,500원 이상 유지 |
| 장비 성장 속도 | 다이아 장비 풀세트(약 24개) 직접 채굴 ≈ 3시간. 상점만으로는 주간 한도 16개라 최소 2주 → 상점은 "보조 수단" | 한도로 속도 조절 |
| 인첸트 | 주민 사서 거래·인첸트 테이블이 원래 주 경로. 상점·뽑기는 이를 빠르게 할 뿐이고, 모루 경험치 비용은 그대로 남는 2차 소비처 | 수선은 고정가 판매 안 함(13.4) |
| 상위권 독주 | 수입이 많은 사람이 희귀품을 싹쓸이 | 1인 주간 한도, 뽑기 하루 한도 |
| 사행성 | 현금 결제가 없으므로 현실 돈 문제는 없음. 그래도 과몰입 방지 | 확률 공개, 하루 한도, 천장(13.5) |

결론: 유저 말대로 **희귀품 판매는 소비를 늘리는 방향**이고, 가격을 "직접 구하는 것보다 비싸게" + 주간 한도만 지키면 야생 가치도 크게 해치지 않는다.

소비 흡수량 예시(1인 주간 최대): 다이아 16개 24,000원 + 인첸트 책 5권 약 20,000원 + 기타 희귀품 약 20,000원 + 뽑기(하루 최대 20회) 최대 280,000원. 주 수입 140,000원인 사람의 돈을 충분히 흡수할 수 있다. 뽑기가 흡수의 대부분을 맡는다.

### 13.3 하이퍼팜 서버 참고 (2026-11-25 hyperf.kr 확인)

### 13.6 구현: 자체 `Market` 플러그인 (권장)

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| EconomyShopGUI에 추가 | 설정만으로 끝. 무료판도 인첸트 책(`enchantments: - "efficiency:4"`) 판매 가능 | 플레이어별 한도(`stock-limit-player`)·구매 시 명령(`buy-commands`)은 **프리미엄 전용**, 랜덤 지급 기능 없음 → 한도·뽑기 불가 | 희귀품에는 부적합 |
| 외부 상자(crate) 플러그인 | 기능 많음 | 26.3을 명시한 검증된 플러그인을 아직 못 찾음, Bank 환불 절차(2.4)와 연동 안 됨 | 보류 |
| **자체 `plugins/market`** | 주간 한도·천장·확률 공개·로그를 우리가 통제. Bank처럼 출금 기록과 대조 가능 | 개발 5–7일(매입 포함, 7.1) | **권장** |

**`plugins/market` (플러그인 이름 `Market`)**

- 의존: `depend: [Vault]`, `softdepend: [Bank]`. 잔액 표시 등 일반 조회는 Vault API, 구매·매입의 출금·입금은 아래의 Bank Java API(거래번호로 한 번만 반영)를 쓴다. 3장의 "Vault로만" 원칙은 EconomyHub·Trade에만 적용.
- 명령: `/희귀상점` (`/market`), `/뽑기` (`/gacha`), `/뽑기 확률`. 관리자: `/market reload`, `/market log <닉>`, `/market reset <닉>`(한도 초기화), 권한 `market.admin`.
- 저장: `plugins/Market/market.db` (파일형 SQLite, Bank와 같은 WAL·`synchronous=FULL`). `purchases(id, time_ms, uuid, item, amount, price, week_key, bank_ref)`, `pulls(id, time_ms, uuid, tier, enchant, level, price, pity_before, bank_ref)`, `pity(uuid, count)`.
- **거래 ID 선기록** (리뷰 반영, 2026-11-25): Vault 출금 뒤에 기록하면 그 사이 장애 때 대조할 기록이 없다. 그래서 모든 구매·뽑기는 Market이 만든 거래 ID(`tx_id`, UUID)를 **Bank보다 먼저** `market.db`에 남기고, 같은 ID를 Bank 거래에 붙인다.
- Bank 추가 기능(Market 개발 때, 스키마 v3): 구 Vault 응답에는 거래번호가 없으므로 Market은 `softdepend: [Bank]`로 Bank의 Java API `withdraw(uuid, amount, source, extRef)`·`deposit(...)`·`findByExtRef(extRef)`를 직접 부른다. `transactions.ext_ref` 유일 제약이라 같은 `tx_id`로 두 번 불러도 **한 번만 반영**되고 처음 결과를 돌려준다. 결과는 세 가지로 돌려준다(5차 리뷰 반영): `OK`, `REJECTED`(잔액 부족·계좌 없음·잠금·종료 중·`BEGIN` 실패처럼 **반영되지 않은 것이 확실한** 실패), `UNKNOWN`(`COMMIT` 실패처럼 반영 여부를 알 수 없는 경우. 지금 Bank는 이때 연결을 닫고 `STORAGE_ERROR`로 묶어 돌려주므로 v3에서 따로 나눈다). `findByExtRef`도 조회 오류를 "없음"과 구분해 `FOUND`/`NOT_FOUND`/`ERROR`로 돌려준다. Bank가 없으면 Market 구매·매입은 잠근다. (3장의 "Vault로만"은 EconomyHub·Trade에만 적용)
- 처리 순서 (구매·뽑기 공통):
  1. 인벤토리 빈칸·한도·잔액 확인 → 하나라도 안 되면 거부(돈 안 빠짐)
  2. 뽑기면 서버에서 결과 확정(`SecureRandom`, 천장 반영)
  3. 한 SQL 트랜잭션: `orders(tx_id, status=PENDING, 품목/결과, 금액)` + 한도·천장 **예약** 차감
  4. Bank 출금(`extRef=tx_id`) → `OK`면 5단계. `REJECTED`면 `ABORTED` + 예약 반환. `UNKNOWN`이거나 예외가 나면 **`PENDING`으로 둔다**(돈이 빠졌는지 모름). 그 플레이어의 Market을 잠그고, 1분마다 `findByExtRef(tx_id)`로 확인해 `FOUND`면 `CHARGED` → 지급, `NOT_FOUND`면 `ABORTED` + 예약 반환, `ERROR`면 그대로 두고 다시 확인한다(10번 연속이면 관리자 목록)
  5. `CHARGED`로 갱신 → 아이템 지급 + 플레이어 PDC `market:applied_tx`에 `<tx_id>#<시도번호>` 추가 → `player.saveData()`(플레이어 파일 즉시 저장) → 디스크 확인(아래) → `FOUND`면 `DELIVERED`. 결과 화면은 연출일 뿐
     - `FOUND`가 아니면(표시 없음이든 읽기 실패든) **같은 틱 안에서 방금 지급한 아이템과 PDC 표시를 회수한다.** 상태는 `CHARGED`(지급 대기)로 두고 시도번호를 올린다
  - 3~5단계는 메인 스레드 한 틱 안에서 끝낸다(자동 저장이 중간에 끼지 않고, 플레이어가 아이템을 옮길 틈도 없음). 같은 플레이어의 거래는 한 번에 하나만.
  - 왜 회수하나 (4차 리뷰 반영): 저장 미확인 때 Market 거래만 잠그면, 플레이어가 미확인 구매품을 상자로 옮긴 뒤 상자만 저장되고 플레이어 파일은 저장에 실패할 수 있다. 그러면 재접속 복구가 같은 상품을 또 준다. 지급과 확인을 한 틱에 묶고 확인 못 하면 그 틱에 회수하면, 확인되지 않은 아이템은 한 번도 플레이어 손을 떠나지 않는다.
- **저장 확인** (3·4차 리뷰 반영): Paper 26.3의 `player.saveData()`는 저장 중 예외가 나도 로그만 남기고 그냥 반환한다(`PlayerDataStorage` 패치). 그래서 호출 뒤 월드 루트의 `players/data/<uuid>.dat`(Bank `PlayerFiles`와 같은 경로 계산)를 직접 열어 읽고, 결과를 **세 가지로 나눈다**:
  - `FOUND`: 파일을 정상으로 읽었고(gzip 해제·NBT 해석 성공, NBT의 `UUID`가 그 플레이어와 같음) `BukkitValues`의 `market:applied_tx`에 해당 표시가 있음
  - `ABSENT`: 정상으로 읽었는데 표시가 없음
  - `UNREADABLE`: 파일 없음, 읽기·gzip·NBT 해석 실패, UUID 불일치. **표시 없음(`ABSENT`)으로 취급하지 않는다**
  - 다음 상태로 넘기는 결정은 `FOUND`일 때만, 거래를 취소하거나 상품을 다시 지급하는 결정은 `ABSENT`일 때만 한다. `UNREADABLE`이면 상태를 그대로 두고 1분마다 다시 읽는다. 10번 연속이면 `/market pending`에 사유를 붙여 올리고 콘솔에 경고하지만, 자동 판단은 계속 `FOUND`/`ABSENT`로만 한다
  - 읽기 클래스는 Bukkit에 의존하지 않게 만들어 단위 테스트한다(정상 파일 표시 있음·없음, 손상된 gzip, 잘린 NBT, 빈 파일, 없는 파일, 다른 UUID)
- **인벤토리 저장 구간까지 복구** (2차 리뷰 반영): 아이템은 플레이어 파일에 저장돼야 확정이다. 그래서 `DELIVERED`는 저장이 디스크에서 확인된 뒤에만 쓰고, "아이템이 저장됐는지"는 DB가 아니라 **아이템과 같은 파일에 저장되는 PDC 표시**(`market:applied_tx`, 최근 32개)로 판단한다.
- 지급 대기(`CHARGED`) 복구 (자동, 관리자 개입 없음):
  - 실행 중(회수한 뒤 같은 접속): 메모리에는 아이템도 표시도 없다. 디스크에 이전 시도 표시가 `FOUND`로 보여도(저장은 됐는데 읽기만 실패했던 경우) 다음 저장 때 메모리 상태로 덮이므로 **믿지 않는다**. 1분마다 다시 지급을 시도한다(새 시도번호로 5단계 반복). 빈칸이 모자라면 알리고 `/market claim`으로 받게 한다
  - 기동 때: 이전 기동의 `PENDING`은 Bank `findByExtRef(tx_id)`로 확인해 출금이 있으면 `CHARGED`, 없으면 `ABORTED`(예약 반환). `CHARGED`는 디스크가 유일한 기준이다. 어느 시도든 표시가 `FOUND`면 그 시도의 아이템이 플레이어 파일에 있으므로 `DELIVERED`, `ABSENT`면 접속 때 다시 지급, `UNREADABLE`이면 그대로 두고 재확인
  - 접속 때(복구가 끝날 때까지 그 플레이어의 Market은 잠금): 메모리 PDC가 아니라 디스크를 직접 읽어 위 기동 때 규칙으로 판단한다
- **Paper가 불러온 파일과 판단에 쓴 파일이 같은지** (5차 리뷰 반영): Paper 26.3은 `.dat` 로드에 실패하면 `.dat_old`(직전 저장본)를 불러온다. 그러면 인벤토리가 비어 있지 않아도 Market이 판단한 최신 파일과 다른 상태로 접속하고, 그 인벤토리가 다시 저장되면 이미 확정한 구매품이 사라질 수 있다.
  - 플레이어 PDC에 `market:seq`(Market이 플레이어 파일에 표시를 쓸 때마다 1씩 올리는 번호)를 둔다. 표시 목록과 함께 같은 파일에 저장되므로 어느 저장본인지 알려 준다
  - 접속 전(`AsyncPlayerPreLoginEvent`, 플레이어 데이터를 불러오기 전): Market 기록이 있는 플레이어면 `.dat`를 직접 읽는다. `UNREADABLE`이면 Paper가 `.dat_old`로 넘어갈 수 있으므로 **접속을 거절**하고(“플레이어 데이터를 확인 중입니다. 관리자에게 문의해 주세요.”) 관리자 목록에 올린다. 읽혔으면 그 `seq`를 기억한다
  - 접속 직후(`PlayerJoinEvent` LOWEST): Paper가 실제로 불러온 PDC의 `seq`가 접속 전에 읽은 값과 다르면(그 사이 Paper만 `.dat`를 못 읽은 경우), 다음 저장이 일어나기 전에 최신 `.dat`를 `plugins/Market/recovery/<uuid>-<시각>.dat`로 복사해 두고 플레이어를 바로 내보낸다. 이후 그 플레이어는 관리자가 확인할 때까지 접속 전 단계에서 거절한다. 같으면 위 접속 때 복구를 진행한다
  - `/market pending`(관리자)은 아직 `CHARGED`·`UNREADABLE`·`REFUNDING`인 거래를 보여 주는 확인용 목록이다. 환불이 필요할 때만 `/market resolve <tx_id> refund`를 쓴다. **Market 출금의 환불 경로는 이것 하나뿐**이다(`/bank refund`는 `source=Market`을 거부, 2.4). Bank 원장의 1회 제약(`transactions.ref` 유일)은 그대로 쓴다 (v0.9.2 리뷰 반영)
  - `/market resolve <tx_id> refund` 순서 (v0.9.2):
    1. `CHARGED`만 받는다(`PENDING`은 기동 복구·1분 타이머가 Bank 출금을 확인할 때까지 기다리라고 안내).
    2. 플레이어 파일을 다시 확인한다. 접속 중이면 먼저 `saveData()`로 지금 상태를 쓴 뒤 읽는다. 어느 시도든 표시가 `FOUND`면 이미 받은 것이므로 `DELIVERED`로 바꾸고 환불하지 않는다(단, 이번 기동에서 회수한 주문인데 표시가 남아 있으면 방금 저장이 실패한 것이므로 판단을 미룬다). `UNREADABLE`이면 환불하지 않는다. `ABSENT`일 때만 다음으로 간다.
    3. 주문을 `REFUNDING`으로 먼저 커밋한다. 이 상태는 지급·복구 경로가 건드리지 않고 플레이어 Market도 계속 잠근다.
    4. Bank `refundByExtRef`. 성공이거나 이미 환불 기록이 있으면 `REFUNDED`로 바꾸면서 **같은 트랜잭션에서 예약했던 주간 한도·하루 뽑기 횟수를 돌려주고 천장을 주문 전 값으로 되돌린다**(받은 것이 없으므로 취소와 같게). Bank가 확실히 거부하면 `CHARGED`로 되돌리고, Bank 꺼짐·잠김·저장 오류처럼 결과를 모르면 `REFUNDING`으로 둔 채 같은 명령을 다시 실행하게 한다(자동으로 되돌리지 않음). 격리된(`quarantined_players`) 플레이어의 주문은 백업 파일 대조 후 `/market resolve <닉|UUID> unquarantine`으로 해제하기 전까지 자동 복구와 환불을 모두 보류한다.
  - 테스트: 구매 직후 `saveData()` 전·후 각각에서 서버 프로세스를 강제 종료 → 재기동·재접속 후 아이템이 정확히 1번만 있고 돈은 1번만 빠졌는지. `players/data`를 읽기 전용으로 바꿔 저장 실패를 재현 → 그 틱에 아이템이 회수되고 `CHARGED`로 남는지, 권한을 되돌리면 다시 지급되는지. 재기동 때 `.dat` 읽기 권한을 막아 `UNREADABLE` → 다시 지급·취소가 일어나지 않는지
- 정수 가격만(2.2). 확률은 설정 파일 `config.yml`의 등급별 `weight`(정수, 합 10,000 = 100.00%)로 두고, 로드 시 합이 10,000이 아니거나 등급 안 책 목록이 비면 **뽑기를 잠근다**.
- 아이템 이동 차단은 EconomyHub와 같은 커스텀 `InventoryHolder` 방식(7.2).

## 14. 서버 매입: 기본가 + 직업 보너스 (v0.8 기획 변경)

> 상태: **확정**(2026-11-25, 14.8). 6.4의 "MVP 매입 없음"을 바꾼다. EconomyShopGUI의 판매 기능은 계속 끄고(6.4), 매입은 자체 `Market`의 `/판매`로만 한다.
> 2026-11-25 개편: "내 직업 품목만 판매"에서 **"모든 매입 품목을 기본가로 판매 + 내 직업 품목은 직업 보너스"**로 바꿨다. 대형 서버에 익숙한 유저에게 "못 판다"보다 "내 직업이면 더 받는다"가 거부감이 적다. 직업 보유 시 받는 금액은 이전 확정가와 같다.

### 14.1 규칙

1. 매입 품목(14.4)은 **누구나 기본가로** 팔 수 있다.
2. **내 직업 2개의 품목은 직업 보너스**(+100–200%, 직업별)가 붙은 가격으로 판다. 단, 그 직업에 가입해 있는 동안 직접 얻은 수량만(14.2).
3. **내가 직접 얻은 것만** 판다. 상점에서 산 것, 자동 농장·주민 거래·상자 전리품으로 얻은 것은 못 판다. 남에게 받은 물건은 본인 판매 가능량만큼만 팔린다.
4. 가격은 **처음엔 보수적으로**, 운영 지표를 보고 단계적으로 올린다(14.5).
5. 1인 **하루 판매 한도**는 모든 품목 합산 5,000원(1단계). 기본가 판매를 열어도 1인 최대 유입량은 그대로다.

효과: 누구나 남는 생산품을 조금은 돈으로 바꿀 수 있고, 제대로 벌려면 직업 품목에 집중해야 해서 분업 동기가 유지된다. 내 직업 밖의 물건은 직접 만들거나 다른 유저에게 사야 하므로 `/trade`를 2단계로 앞당긴다(14.8).

### 14.2 "직접 얻었는지" 판정: 판매 가능량 기록

아이템에 표시(NBT)를 붙이는 대신, **플레이어별로 "직접 얻은 수량"을 DB에 기록**하고 팔 때 그만큼 차감한다.

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 아이템에 획득자 표시(PDC) | 아이템마다 출처가 정확 | 표시가 있는 아이템과 없는 아이템이 **겹쳐지지 않음**(같은 다이아가 두 칸으로 나뉨), 정렬 플러그인·상자·화로와 충돌, 녹이거나 조합하면 표시가 사라짐 | 비권장 |
| **판매 가능량 기록** | 아이템은 바닐라 그대로(겹치기·보관 정상), 구현 단순 | "어느 다이아가 내 것인지"는 구분 안 함. 단, 팔 수 있는 총량은 **내가 직접 생산한 양을 넘지 못하므로** 결과는 같음 | **채택** |

**기록은 직업과 상관없이 모든 플레이어에게** 남기되, 얻은 순간 그 품목의 직업에 가입해 있었는지로 두 칸에 나눠 쌓는다.

- `job_amount`: 그 직업에 가입한 상태로 얻은 수량 → **보너스가**로 판매
- `base_amount`: 가입하지 않은 상태로 얻은 수량 → **기본가**로 판매

예: 낚시꾼이 아닌 광부가 대구 10마리를 낚으면 `base_amount[대구] += 10`(기본가 4원). 나중에 낚시꾼으로 바꿔도 이 10마리는 기본가 그대로다. 그래서 **"직업 없이 모아 두었다가 직업만 바꿔 보너스로 파는" 우회가 원천적으로 안 된다.** 직업을 탈퇴하면 그 직업의 `job_amount`는 `base_amount`로 옮겨진다(삭제하지 않음, 보너스만 사라짐).

**기록되는 경우**

| 카테고리 | 기록 조건 | 기록 안 됨 |
| --- | --- | --- |
| 광부 | 자연 생성 광석을 플레이어가 캐서 떨어진 아이템(행운 포함 실제 드롭 수) | 설치한 광석, 실크터치로 캔 광석 블록, 피스톤으로 옮긴 광석 |
| 벌목꾼 | 플레이어가 벤 자연·묘목 성장 원목 | 설치한 원목 |
| 농부 | 다 자란 작물을 플레이어가 수확한 드롭, 줄기에서 자란 호박·수박 블록 | 덜 자란 작물, 피스톤·주민·물 수확, 설치한 호박·수박 |
| 사냥꾼 | 플레이어가 막타를 친 자연 스폰 몹의 드롭 | 스포너 몹(`fromMobSpawner`), 동물·주민 |
| 낚시꾼 | 낚시로 건진 아이템(`PlayerFishEvent` CAUGHT_FISH) | AFK 판정 중 낚시 |

- **생산자 규격 확인·자체 비트맵 fallback 및 형식 불명 fail-closed** (v0.9.3, **2026-11-26 확정**): EconomyHub 가 없어도 희귀 상점·뽑기가 동작하도록 `plugin.yml` 의 `EconomyHub` 의존성은 `softdepend` 로 유지한다.
  - 블록 판매 가능량 집계(광부·벌목꾼·농부)는 EconomyHub 가 활성화되어 있고 `economyhub-block-marks-v1` 규격(`provides`)을 제공할 때만 수행된다. Hub 가 꺼져 있거나 구버전(규격 미지원)이면 블록 판매 가능량 집계를 차단하고 `/market status`에 이유를 표시한다(사냥·낚시는 영향 없음).
  - Hub 중단 구간 대비 fallback: Market 도 자체 청크 PDC 비트맵(`market:u<구역 y>`, `long[64]`)에 블록 배치를 기록하여(`BlockPlaceEvent` MONITOR), Hub 중단 중 놓인 블록도 추후 채광 시 자연산으로 집계되지 않도록 보호한다. 블록 판정 시 두 비트맵을 결합하여 둘 중 하나라도 설치 표시/판정 불가면 제외한다.
  - 손상 배열 보존: 청크 PDC 비트맵 길이가 64가 아니거나 타입이 다르면 덮어쓰지 않고 보존하며 fail-closed 로 판정 불가(`UNKNOWN`) 처리하고 1회 경고 로그를 남긴다.
- **씨앗 겸용 작물** (v0.9.2 리뷰 반영, **2026-11-26 확정**): 감자·당근·네더 사마귀·코코아 콩은 수확물과 심는 씨앗이 같은 아이템이라, 드롭 전체를 적으면 다시 심은 1개만큼 판매 가능량이 실제 남는 양보다 수확마다 1개씩 많이 쌓인다(농부 Lv.10 자동 재파종도 드롭에서 1개를 떼어 심음). 그래서 다 자란 작물 한 칸 수확마다 그 아이템을 **1개 빼고** 적는다(0 미만 없음, 독 감자 등 다른 드롭은 그대로). 직접 다시 심지 않아도 똑같이 빼므로 판매 가능량이 "적게" 잡히는 쪽으로만 틀린다. 밀·비트는 씨앗이 다른 아이템이라 보정하지 않는다.
- 제련품은 사지 않는다: 철·금·구리는 **원석**(raw)으로만 매입. 블록 형태(다이아 블록 등)도 매입 안 함.
- 직업 변경 쿨타임 1시간(5.1)을 둔다. 우회 방지는 위 두 칸 기록이 맡고, 쿨타임은 잦은 직업 변경 자체를 줄이는 용도다.
- 플레이어 직업 조회: VJobs API 또는 PlaceholderAPI로 현재 직업 2개를 읽는다(14.8 1순위 확인).
- **탈퇴 이관 보정**: VJobs에 탈퇴 이벤트가 없거나 DB·PlaceholderAPI로 우회하면 탈퇴 순간을 못 잡을 수 있다. 그래서 **접속할 때와 `/판매`를 열 때마다** 현재 직업을 조회해, 보유하지 않은 직업 카테고리에 `job_amount > 0`이 남아 있으면 그 자리에서 `base_amount`로 옮긴다. 판매 직전에도 같은 확인을 한다. 탈퇴 이벤트가 있어도 이 보정은 그대로 둔다. 접속 직후 VJobs가 아직 직업 정보를 불러오지 못했으면 1초 간격으로 최대 30번 다시 시도한다. VJobs는 켜져 있는데 직업 정보를 못 읽은 동안에는 `/판매` 버튼을 `직업 정보를 불러오는 중`으로 막고 판매도 거부한다(보너스가 빠진 기본가로 잘못 팔리지 않게, v0.9.2).
- **일괄 반영 버퍼 (구현 메모)**: 판매 가능량 기록은 메인 스레드 fsync 부하를 줄이기 위해 메모리 버퍼에 모아 20틱(1초)마다 한 트랜잭션으로 반영한다(판매 시작·`/판매` 열기·탈퇴 보정·퇴장·서버 종료 시 해당 플레이어 또는 전체 버퍼를 먼저 반영). 서버가 강제 종료되면 최대 1초 치 기록을 잃을 수 있으나, 판매 가능량이 "적게" 잡히는 방향이라 경제상 안전하다.

### 14.3 판매 처리 순서 (`/판매` GUI)

1. 5개 카테고리 탭을 모두 보여준다. 내 직업 2개 탭은 초록색으로 강조하고 `[직업 보너스 +150% 적용 중]`, `기본 4원 → 10원`처럼 함께 표시한다.
2. 품목마다 "가진 수량 / 보너스 판매 가능량 / 기본 판매 가능량 / 오늘 남은 한도"를 표시한다.
3. **보너스분부터, 묶음 단위로 따로** 계산한다. 한 묶음 안에서 두 칸을 섞지 않는다(섞으면 감자 16개 묶음이 6.5원처럼 소수가 됨). 모두 정수 나눗셈:
   1. 보너스 묶음 수 = min(인벤토리 ÷ 단위, `job_amount` ÷ 단위, 남은 한도 ÷ 묶음당 보너스가)
   2. 기본 묶음 수 = min(남은 인벤토리 ÷ 단위, `base_amount` ÷ 단위, 남은 한도 ÷ 묶음당 기본가)
   3. 한 번에 둘 다 팔리면 `sales`에 `price_type`별로 1줄씩(총 2줄) 기록
4. 한 SQL 트랜잭션: `sales`에 `tx_id`(UUID)·품목·수량·금액을 `PENDING`으로 기록 + 판매 가능량·하루 한도 **예약** 차감 (13.6과 같은 선기록)
5. 인벤토리에서 아이템 제거(칸별 원래 상태를 기억) + 플레이어 PDC `market:applied_tx`에 `<tx_id>#<시도번호>` 추가 → `player.saveData()` → 디스크 확인(13.6 저장 확인, 세 가지 결과)
   - `FOUND` → `ITEMS_TAKEN` → 6단계
   - 그 외 → **아이템을 돌려주지 않고 보류한다**(5차 리뷰 반영). 메모리의 인벤토리는 "아이템 빠짐 + 표시 있음" 그대로 두고, 상태는 `PENDING`(저장 확인 대기), 입금은 하지 않는다. 빠진 아이템은 `market.db`에 기록만 해 두고 플레이어에게는 "판매 처리 중(저장 확인 대기)"이라고 알린다
   - 왜 돌려주지 않나: 저장은 됐는데 확인용 읽기만 실패한 경우, 돌려준 아이템을 상자로 옮기고 상자만 저장된 채 서버가 꺼지면 재기동 복구가 플레이어 파일의 제거 표시를 보고 대금까지 입금한다(아이템 + 돈). 보류하면 메모리와 앞으로의 저장이 항상 "아이템 빠짐 + 표시 있음"이라, 결과는 "입금"이나 "디스크에 남은 아이템으로 복귀" 중 하나뿐이다
6. Bank 입금(`extRef=tx_id`) → `DONE`. 4~6단계는 메인 스레드 한 틱 안에서 끝낸다
7. 아이템 제거 전 실패는 `ABORTED` + 예약 반환. 입금이 실패하면(Bank 잠금 등) `ITEMS_TAKEN`으로 두고 같은 `tx_id`로 다시 입금한다(아이템을 돌려주지 않음, 중복 입금 없음)
8. 정수 가격만(2.2). 싼 품목은 **묶음 단위 가격**(예: 감자 16개당 기본 4원, 보너스 8원)으로 두고 묶음 단위로만 판다

**인벤토리 저장 구간까지 복구** (2·3·4차 리뷰 반영): 아이템 제거도 플레이어 파일에 저장돼야 확정이다. `DONE`을 먼저 쓰고 저장 전에 서버가 꺼지면 아이템은 인벤토리로 돌아오고 돈은 남아 복제가 된다. 그래서 입금과 `DONE`은 디스크에서 표시를 `FOUND`로 확인한 뒤에만 하고, 취소(`ABORTED`)는 디스크를 정상으로 읽었는데 표시가 없을 때(`ABSENT`)만 한다. 읽기 실패(`UNREADABLE`)는 어느 쪽으로도 확정하지 않는다. 복구는 자동이다:

- 실행 중(보류 중인 같은 기동): 1분마다 `saveData()`를 다시 부르고 디스크를 읽어 `FOUND`면 `ITEMS_TAKEN` → 입금 → `DONE`. `ABSENT`·`UNREADABLE`이면 그대로 기다린다. 실행 중에는 취소하지 않는다(메모리에는 아이템이 빠져 있어서, 취소하면 다음 저장 때 아이템도 돈도 없어짐)
- 기동 때: 이전 기동의 `ITEMS_TAKEN`은 같은 `tx_id`로 Bank 입금(이미 있으면 처음 결과를 돌려받음) → `DONE`. `PENDING`은 디스크가 유일한 기준이다. 어느 시도든 표시가 `FOUND`면 디스크에서 아이템이 빠진 것이므로 `ITEMS_TAKEN` → 입금 → `DONE`, `ABSENT`면 디스크에 아이템이 남아 있으므로 `ABORTED` + 예약 반환(플레이어는 디스크의 아이템으로 접속), `UNREADABLE`이면 `PENDING`으로 두고 1분마다 재확인(10번 연속이면 관리자 목록). 플레이어가 접속하지 않아도 됨
- 접속 때: 13.6과 같이 디스크를 직접 읽어 기동 때 규칙으로 판단한다. 접속 전·직후 파일 일치 확인(13.6, `.dat_old` 대비)도 같다
- 격리된 플레이어(`quarantined_players`): 디스크 불일치로 격리된 플레이어의 판매는 해제 전까지 자동 복구(입금·취소)를 모두 보류한다(13.6과 동일)
- 입금 결과가 `UNKNOWN`이거나 예외가 나면 `ITEMS_TAKEN`으로 두고 1분마다 같은 `tx_id`로 다시 입금한다(한 번만 반영되므로 중복 없음)
- 테스트: 판매 직후 `saveData()` 전·후와 입금 전·후에서 각각 강제 종료 → 재기동·재접속 후 "아이템 있음 + 돈 없음" 또는 "아이템 없음 + 돈 1번" 중 하나만 나오는지. `players/data` 읽기 전용으로 저장 실패를 재현해 아이템이 돌아오지 않고(보류) 입금도 없는지, 권한을 되돌리면 1분 안에 입금되는지, 그 상태로 재기동하면 아이템 복귀(돈 없음)가 되는지. 재기동 때 `.dat` 읽기를 막아 `UNREADABLE` → `ABORTED`가 되지 않고 대기하는지. `.dat`를 손상시켜 접속 → 접속 전 단계에서 거절되는지

- **전 직업을 똑같이 올리지 않는다.** 직전 기간 데이터에서 **하루 한도 소진율이 낮고 목표 비율(14.4)에 못 미치는 직업만** 올린다. 목표 비율을 넘은 직업은 그대로 두거나 내린다.
- 인상 조건: 총 통화량 증가가 희귀 상점·뽑기 소비로 흡수되고 있고(10장), 다이아 시세가 무너지지 않음.
- 배율을 곱한 단가는 **정수로 내림**(2.2). 예: 원목 보너스가 3원 ×1.5 = 4원. 이 계산은 문서 PR에서 하고, `config.yml`에는 결과 정수만 적는다(14.7).
- 어느 단계에서도 품목별 **상한(상점 구매가의 25%)**을 넘지 않는다. 특히 **에메랄드는 최대 75원**, 원목 5원, 이름표 375원, 안장 300원에서 멈춘다.
- 내리는 것은 바로 할 수 있게, 올리는 것은 이 문서를 고치는 PR로만.

### 14.6 다른 장과의 관계

- **6.1 1번(매입가 ≤ 구매가 25%)**: 14.4의 품목별 상한으로 단계 인상 후에도 지킨다(에메랄드 75원 등).
- **6.1 4번(자동 생산 자원 매입 금지)**: 판매 가능량은 플레이어가 직접 캔·수확한·잡은 것만 기록하므로, 철 골렘 농장·피글린 금 농장·주민 생산분은 애초에 팔 수 없다. 그래서 철·금 원석처럼 농장으로도 얻을 수 있는 자원도 "직접 캔 원석"에 한해 매입한다.
- **4.1 경제 기준**: 매입은 새 돈 공급원이다(1장 5번 원칙의 근거 문서가 이 장). 1단계 기준 직업 + 보너스가 매입 합산 시간당 약 8,300원(사냥꾼)–11,000원(벌목꾼), 하루 한도 5,000원이 상한.
- **2.4 환불**: 매입은 입금이라 `/bank refund` 대상이 아니다. `market.db` 판매 기록으로 확인 후 `/bank give`.

### 14.7 구현

`plugins/market`(13.6)에 `/판매`(`/sell`)를 추가한다. 추가 DB 테이블: `sell_quota(uuid, item, job_amount, base_amount)`, `sales(id, time_ms, uuid, item, amount, price_type(base|bonus), unit_price, total, bank_ref)`, `daily_sales(uuid, day_key, total)`. 품목→카테고리(직업) 매핑, 묶음 단위, 한도는 `config.yml`. **가격은 배율을 런타임에 곱하지 않고** 품목마다 `base_price`·`bonus_price`·`max_price`를 계산·내림·상한 적용이 끝난 **최종 정수값으로 직접** 적는다(단계 인상은 어차피 이 문서 PR로만 하므로, 그 PR에서 표와 `config.yml`을 같이 고침). 로드 검증은 정수 여부와 `base_price ≤ bonus_price ≤ max_price`만 확인하고, 하나라도 어긋나면 매입을 잠근다. 개발은 희귀 상점·뽑기 2–3일 + 매입 3–4일, 합쳐 **5–7일**(7.1).

악용 체크(8장에 추가): 설치 광석 재채굴, 실크터치 → 설치 → 행운 채굴, 상점 구매품 판매 시도, **비직업으로 모은 뒤 직업 가입 → 보너스가로 판매 시도(기본가로만 팔려야 함)**, 직업 탈퇴 → 보너스가 판매 시도(기본가로만), 하루 한도 직전 연타, 판매 중 강제 종료.

PlaceholderAPI는 필요 없다.

## 15. 직업 레벨 편의 스킬 (v0.9 기획 추가)

> 상태: **기획 확정**(2026-11-25). 개발은 2.5a(Lv.10·20 + 토글 GUI)와 2.5b(Lv.30·50 연쇄 파괴류 + 칭호)로 나눈다(7.1).
> 5.1의 "전투 능력치 특전 없음"과 2.2의 "정수 보상 유지(레벨 수입 보너스 0%)"는 그대로 유지한다.

### 15.1 왜 추가하나

- 직업 레벨(최대 50, 누적 약 141시간)이 올라가도 실질 혜택이 없어, 초반 이후 레벨링 동기가 약하다.
- 레벨당 수입 배율(+%)은 정수 화폐 원칙(2.2)과 충돌하고, 후반 인플레이션과 선발대·후발대 격차를 키운다.
- 대신 **1회 보상 단가는 그대로 두고 반복 작업의 피로(재파종·줍기·동선·정리)만 줄이는 편의 스킬**을 레벨에 따라 연다.

### 15.2 원칙

1. **보상 단가는 불변이며, 편의 스킬로 인한 시간당 수입 상승은 목표 구간(7,000–12,000원) 내 최대 약 +15% 이내로 관리한다.** VJobs 1회 보상(5.2)과 Market 매입가·하루 한도(14.4)는 레벨과 무관하다. 작업이 빨라지는 스킬(연쇄 파괴, 입질 단축)의 효과는 테스트 서버에서 실측한다(15.4).
2. **전투 능력치 없음**: 공격력·체력·방어력 증가는 두지 않는다. 야간 투시·이동 속도 같은 편의 효과만.
3. **현재 직업 2개에만 적용**: VJobs API로 가입 직업·레벨을 확인(1초 캐시, 가입·탈퇴·레벨업 이벤트 때 즉시 갱신). 탈퇴하면 바로 꺼지고, 재가입하면 유지된 레벨대로 다시 열린다.
4. **개별 토글**: 스킬마다 켜고 끈다(플레이어 PDC `economyhub:skill_toggle.<id>`). 서버 전체에서 끌 스킬은 `config.yml` `skills.disabled`.
   - **기본 꺼짐**: 연쇄 파괴 3종(광맥 채굴·일괄 벌목·3×3 수확)과 쓰레기 자동 필터. 의도치 않은 대량 파괴·아이템 폐기를 막기 위해 플레이어가 직접 켠다.
   - **기본 켜짐**: 그 밖의 스킬(자석, 재파종·재식재, 동굴 시야, 입질 알림 등).
5. **서바이벌·모험 모드에서만** 동작한다.

**설치 블록 기록 (연쇄 파괴·Market 공유 전제)**
- VJobs 설치 기록은 공개 API가 없고, EconomyHub는 지금 피스톤·유체로 생긴 블록만 표시한다(7.2).
- EconomyHub가 **플레이어가 설치한 광석·원목·호박·수박**의 좌표를 피스톤·유체 표시와 같은 청크 PDC 비트맵(`economyhub:u<구역 y>` 방식)에 기록하고, 그 블록을 캐면 지운다. 피스톤으로 밀면 표시도 도착 좌표로 옮긴다.
- **Market(14.2)도 같은 기록을 읽어** 판매 가능량에서 뺀다(기록을 두 곳에 두지 않음).
- **Market 1.7을 개발할 때 EconomyHub에 먼저 만든다.** Lv.10·20 스킬은 이 기록을 쓰지 않으므로, 2.5a를 1.5와 함께 먼저 구현했어도 기록은 1.7(늦어도 2.5b 연쇄 파괴 전)에 만든다.

**Lv.10·20 (2.5a)**
- **자석**은 원래 이벤트를 취소하지 않고 떨어질 아이템만 옮긴다. 블록 드롭은 `BlockDropItemEvent` HIGHEST(Market이 NORMAL–HIGH에서 직접 획득 수량을 먼저 기록), 몹은 `EntityDeathEvent` HIGHEST(경험치는 `giveExp(xp, true)`로 수선 적용), 낚시는 VJobs·Market이 `PlayerFishEvent`를 다 읽은 다음 틱. 인벤토리가 가득 차면 남은 분량만 바닥에
- 재식재는 밑동부터 이어진 같은 종류의 원목(대각선 포함, 최대 64개)에 자연 잎(네더는 해당 사마귀 블록)이 붙어 있을 때만 한다. 아카시아·벚나무처럼 줄기가 꺾이는 나무도 포함. 위쪽 원목을 먼저 벤 경우를 위해, 같은 기둥(x·z)의 원목에서 수관을 확인하면 30초 동안 기억해 밑동을 나중에 베도 심는다. 잎 없는 건축 기둥이나 수관을 먼저 제거한 나무에는 심지 않는다. 기본 켜짐을 유지한다.
- 스킬 토글은 일반 좌클릭에서만 변경한다. 숫자키·F·Q·더블클릭·Shift 클릭은 메뉴 동작을 실행하지 않는다. 동굴 시야 적용 중 긴 물약을 사용한 직후 퇴장해도 재접속 시 물약 시간이 유지되어야 한다.
- **재파종 씨앗**: 그 작물의 드롭(`BlockDropItemEvent`, 자석보다 먼저)에서 씨앗 1개를 먼저 떼어 쓰고, 드롭에 없을 때만 인벤토리에서 쓴다(Lv.10–19는 수확물 자석이 없어 첫 수확부터 심기게). 심지 못하면 뗀 씨앗은 그 자리에 다시 떨군다
- **해금 안내**: 가입·레벨업 뒤 새로 열린 스킬을 채팅으로 한 번 알린다(이름·켜짐 여부·`/직업 → 스킬 설정`). 안내 여부는 PDC `economyhub:skill_notified.<id>`라 재가입해도 다시 보내지 않는다
- **재파종·재식재**: `BlockBreakEvent`를 통과시킨 뒤 1틱 후 그 자리가 비어 있고 받침(경작지·영혼 모래·정글 원목·흙)이 그대로일 때만 인벤토리의 이름 없는 기본 아이템 1개를 써서 나이 0으로 심는다(코코아는 방향 유지). 아이템이 없으면 심지 않음(복사 없음)
- **나뭇잎 급속 소멸**: 원목을 벤 10틱·30틱 뒤 반경 6 안에서 **`!isPersistent()`이고 `distance == 7`인 잎만** 모아 틱당 16개씩, 바닐라와 같은 `LeavesDecayEvent`를 내고 정리(CoreProtect 기록·다른 플러그인 취소 존중). 플레이어가 설치한 장식용 잎(persistent)과 옆 나무의 살아 있는 잎(distance < 7)은 건드리지 않는다
- **괭이 우클릭 수확**: `player.breakBlock`으로 부숴 VJobs 보상·재파종·자석·CoreProtect가 실제 채집과 같게 동작. 웅크리기 우클릭은 Lv.30 3×3용으로 비워 둔다
- **동굴 시야**: 오버월드에서만, 2초마다 눈높이 블록이 `Y ≤ 50`이고 `getLightFromSky() == 0`이면 야간 투시 15초(300틱, 입자·아이콘 없음)를 갱신한다(지상의 밤·트인 협곡에서는 켜지지 않음).
  - **물약 보호**: 남은 시간이 **300틱을 넘는 기존 야간 투시는 덮어쓰지 않는다**(물약·무한 효과 유지).
  - **스킬이 직접 건 효과만** 조건 해제·토글 끔·탈퇴·접속 종료·플러그인 종료 때 지운다. 스킬이 건 효과를 그 사이 물약이 덮으면 그 효과는 플레이어 것으로 보고 지우지 않는다
- **사냥감 탐지**: 검 또는 활을 든 채 웅크리기 + **허공 좌클릭**(`LEFT_CLICK_AIR`)으로 발동. 반경 24블록 적대 몹에 바닐라 `GLOWING` 6초(쿨 12초)
- **GUI**: `/직업`(45칸) 40번은 1.5단계 `/직업` 확정 레이아웃(7.2, 상세 슬롯은 1.5 PR과 함께 7.4.2에 추가)대로 규칙·쿨타임 상태(`CLOCK`)를 유지하고, **42번 칸**에 `스킬 설정`(`BOOK`)을 둔다. 27칸 `직업 스킬 관리`: 1줄 1번에 첫 직업 아이콘, 3–6번에 그 스킬, 2줄 10번에 둘째 직업, 12–15번에 스킬. 켜짐 `LIME_DYE`, 꺼짐 `GRAY_DYE`, 미해금 `IRON_BARS` + `Lv.N에 해금`, 서버에서 끈 스킬 `BARRIER`. 3줄 18번 `/직업`으로, 22번 안내, 26번 닫기

**Lv.30·50 (2.5b)**
- **연쇄 파괴 공통**(광맥 채굴·일괄 벌목·3×3 수확): 설치 블록 기록에 있는 블록은 건너뛴다. 블록마다 `player.breakBlock`으로 부숴 VJobs 보상·CoreProtect·자석이 한 칸씩 캔 것과 같게 동작하고, 플레이어별 재귀 가드로 스킬이 부순 블록이 다시 연쇄를 일으키지 않게 한다.
- **일괄 벌목 발동 조건**: 운영 월드에는 설치 블록 기록 도입 전에 지은 목조 건축물이 있어 기록만으로는 막지 못한다. 그래서 연결된 원목 묶음 둘레(각 원목의 이웃 칸)에 `!isPersistent()` 자연 나뭇잎이 **1개 이상 붙어 있을 때만** 발동하고, 없으면 그 한 칸만 벤다.
- **호박·수박 줄기 보호**(농부 Lv.50): `PUMPKIN_STEM`·`ATTACHED_PUMPKIN_STEM`·`MELON_STEM`·`ATTACHED_MELON_STEM`을 웅크리지 않은 채 캐면 `BlockBreakEvent`를 취소한다(웅크리면 정상적으로 캐짐).
- **낚시 중 야간 투시**(낚시꾼 Lv.50): 그 플레이어의 찌(`FishHook`)가 월드에 있는 동안 야간 투시를 건다. 동굴 시야와 같은 규칙(300틱 넘게 남은 효과는 덮어쓰지 않음, 스킬이 건 효과만 해제)이고, 찌가 사라지면 다음 확인(2초) 때 지운다.
- **광맥 채굴**: 일반 광석과 `DEEPSLATE_*_ORE`를 같은 묶음으로 본다(예: `IRON_ORE` ↔ `DEEPSLATE_IRON_ORE`). 다음 경우 **즉시 중단**: 도구 내구도가 1 남음, 도구가 부서짐, 손에 든 도구가 바뀜.
- **사냥꾼의 추격**: 자연 적대 몹 처치 시 신속 I 5초(쿨 3초)만. 배고픔 회복은 하지 않는다.
- **Lv.50 칭호**: VJobs의 Lv.50 칭호 설정(`titles."50"`)을 재사용하고 이름을 `[전설의 광부]`·`[전설의 벌목꾼]`·`[전설의 농부]`·`[전설의 사냥꾼]`·`[전설의 낚시꾼]`으로 바꾼다. **채팅 닉네임 앞에만** 표시하고 탭 목록에는 표시하지 않는다.

### 15.6 테스트 (8장에 추가)

- 2.5a: 각 자석 켜고 캔 뒤 인벤토리 직행, 인벤토리 가득 찼을 때 남은 분량만 바닥에 / 씨앗·묘목 0개로 재파종·재식재 → 안 심김(복사 없음) / 장식용 나뭇잎(설치) 옆 원목 베기 → 그 잎 그대로, 옆 나무 잎 그대로 / 야간 투시 물약(8분) 마신 뒤 동굴 출입 → 물약 시간 유지 / 동굴 시야 켠 채 탈퇴 → 2초 안에 야간 투시 사라짐 / 밤의 지상·Y 30 트인 협곡 → 동굴 시야 안 켜짐 / 사냥감 탐지: 검·활 웅크리기 허공 좌클릭 → 발광, 활 당기기에는 발동 안 함 / 토글 끄고 재접속·재시작 → 유지, 첫 접속 시 쓰레기 필터 꺼짐 / 크리에이티브에서 스킬 안 켜짐 / 스포너 몹은 자석 안 됨 / Market 개발 후 자석 켜고 `/판매` → `sell_quota` 정상 누적
- 설치 블록 기록: 광석·원목·호박 설치 → 채굴 → VJobs 0원, Market 판매 가능량 미증가 / 설치 후 피스톤으로 밀기 → 동일 / 재시작 후에도 유지
- 2.5b: 설치·피스톤 이동 광석/원목으로 연쇄 파괴 → 1칸도 안 됨 / 설치 블록 기록 이전에 지은 통나무집(주변 자연 나뭇잎 없음)에서 일괄 벌목 미발동, 한 칸만 베임 / 웅크리지 않고 호박 줄기 캐기 → 안 캐짐 / 찌를 던지면 야간 투시, 거두면 2초 안에 사라짐 / 내구도 3 곡괭이로 광맥 6개 → 내구도 1에서 중단 / 광맥 채굴 중 핫바 전환 → 중단 / 철광석·심층암 철광석이 섞인 광맥 → 한 묶음으로 채굴 / 연쇄 3종 첫 접속 시 꺼짐 / 사냥꾼의 추격 후 배고픔 그대로 / Lv.50 칭호가 채팅에만 나오고 탭 목록에는 없음
