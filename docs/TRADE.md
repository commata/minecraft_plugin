# `/trade` 1:1 교환 — 로직 설계 (Trade 플러그인)

> 상태: **로직 설계 v4** (2026-11-27). v3(33334a8) 재검증에서도 예외 덧대기(킥·인벤토리 전체 차감·발밑 드롭)가 새 Critical 을 만들어, 정산을 **이미 QA를 통과한 Market 의 "판매(가져오기) + 구매(지급)" 흐름**으로 다시 짬(13장). 아이템이 거래 중(OPEN)에 움직이지 않는 제시 방식(v2, 사용자 결정)은 그대로. v1(4e70587)·v2(f4c2cd0)·v3 기록은 11·12장.
> 단계: ① 로직 설계(이 문서) → ② GUI 설계(7.4.6) → ③ 구현(DEV) → ④ QA(Level 4) → ⑤ 피드백 수정 → 테스트 서버 검증 → 운영 첫 배포에 포함(STATUS.md 7장).

## 0. 핵심 원칙

1. **거래 중(OPEN·COUNTDOWN)에는 아이템이 인벤토리에서 움직이지 않는다**(제시 방식, 사용자 결정). 이때 취소·로그아웃·강제 종료는 아무것도 바꾸지 않는다.
2. **정산은 Market 의 검증된 두 흐름을 그대로 쓴다**: ① 가져오기 = Market `/판매`(의도 기록 → 인벤토리에서 빼고 토큰 → 저장 → 디스크 확인, 확인 전엔 돌려주지 않음), ② 지급 = Market 구매품 지급(같은 틱에 지급·토큰·저장·디스크 확인, 실패하면 같은 틱에 회수하고 대기, 나중에 새 시도 번호로 다시). 맡긴 아이템은 **저널이 보관**한다(fsync).
3. 판정은 **디스크 `.dat`** 로만: `FOUND`(토큰 있음) / `ABSENT`(파일을 읽었고 토큰 없음, 확정) / `UNREADABLE`(파일을 못 읽음, 모름). 모름은 기다리고 잠근다(AGENTS.md 2.7·2.8). 접속 중인 메모리 토큰은 판정에 쓰지 않는다.
4. 월드에 떨어뜨리지 않고, 플레이어를 내보내지 않고, 인벤토리를 뒤져 대신 빼지 않는다.

## 1. 범위

- 새 플러그인 `plugins/trade`, `plugin.yml` 이름 **`Trade`**, 패키지 `kr.commata.trade`.
- 의존: `depend: [Vault]`, `softdepend: [Bank, Travel, EconomyHub]`. Bank가 없거나 잠기면 **거래 기능 전체 잠금**(10장 5).
- 명령: `/trade` (`/거래`) 접속자 선택 창, `/trade <닉네임>` 요청, `/trade accept|deny [닉네임]`, `/trade claim`(받지 못한 물건 수령, 8장), `/trade status`·`/trade reload`·`/trade resolve <tradeId>|unlock`(관리자). 권한 `trade.use`(기본 모두), `trade.admin`(op).
- **크리에이티브·관전 모드에서는 요청·수락·정산 불가**(크리에이티브 아이템이 서바이벌 경제로 들어오는 것 방지, ECONOMY.md 8장 "크리에이티브 보상"과 같은 원칙).

## 2. 세션 상태와 세대

```
 (없음) ─/trade B─▶ REQUESTED ─30초·거절·한쪽 종료─▶ (없음)        재요청 금지 10초(10장 4)
                       │ 수락
                       ▼
                     OPEN ◀──────────── 변경·준비 해제·대화창 열림 ───┐
                       │ 양쪽 준비                                     │
                       ▼                                               │
                   COUNTDOWN (3초) ─────────────────────────────────────┘
                       │ 0초
                       ▼
                   SETTLING ──REJECTED(잔액 부족 등)──▶ CANCELLED
                       │ 커밋 지점(5장 3)
                       ▼
                   COMMITTED ──양쪽 반영 확인──▶ COMPLETED
```

- 한 플레이어는 세션 하나(보낸 요청·받은 요청 포함). **정산 기록(저널)이 남은 플레이어**는 새 요청·수락 불가.
- 세션은 `tradeId`(UUID)와 **세대 번호 `gen`** 을 가진다. **아이템·금액(제시 내용)이 바뀔 때만** `gen += 1` + 양쪽 준비 해제 + 카운트다운 취소. 준비 토글은 `gen`을 올리지 않는다(자기 준비만 바뀜, 해제하면 카운트다운만 취소) — 그래야 양쪽 준비에 도달한다. 대화창 응답·카운트다운 틱·지연 작업은 시작할 때의 `(tradeId, gen)`을 들고 있다가 **다르면 무시**(QA High #4).
- 종료 사유(사망, 로그아웃·강퇴·화이트리스트 제거로 인한 퇴장, 창 닫기, 취소 버튼, 전투 태그, 모드 변경, 플러그인 종료)는 **이벤트 안에서 즉시** 세션을 CANCELLED로 바꾼다(창 닫기 같은 화면 처리만 다음 틱). OPEN/COUNTDOWN 에서는 아이템이 안 움직였으므로 그걸로 끝. SETTLING 이후에는 취소하지 않고 5장대로 진행.
- 서버 재시작: REQUESTED·OPEN·COUNTDOWN 은 메모리에만 있으므로 그냥 사라진다(아이템 영향 없음). SETTLING·COMMITTED 는 저널로 복구(6장).
- 전투: 요청·수락·준비·정산 직전에 Travel PDC `home:combat_until` 확인(키 이름 고정, AGENTS.md 2.4). Travel 이 없으면 검사 생략 + `/trade status` 표시. 차원 이동·텔레포트는 취소 사유가 아님(7.3 거리 제한 없음, 아이템이 안 움직이므로 위험 없음).

## 3. 제시 (아이템)

- 제시 = `(내 인벤토리 칸 번호, 그 칸 아이템의 스냅샷, 제시 개수)`. 한 칸은 한 번만, 최대 16칸(7.4.6 4×4).
- 조작(② GUI 설계에서 확정): 아래 내 인벤토리 칸 좌클릭 = 그 칸 전부 제시, 우클릭 = 1개 추가. 위 "내 제시 칸" 좌클릭 = 빼기, 우클릭 = 1개 빼기. **아이템은 실제로 움직이지 않음** — 거래 창은 `common.gui` 처럼 모든 클릭을 취소하고 위 동작만 해석한다(v1의 "본인 칸 넣고 빼기 예외"는 없어짐).
- 창이 열려 있는 동안 플레이어는 인벤토리를 직접 조작할 수 없지만, 땅의 아이템 줍기·다른 플러그인 지급으로 칸 내용이 바뀔 수 있다. 그래서 **매 틱·정산 직전에 "그 칸에 같은 아이템(isSimilar)이 제시 개수 이상 있는지"** 를 다시 확인하고, 달라졌으면 그 제시를 지우고 `gen += 1`(준비 해제) + 안내.
- 거래 가능: 바닐라 아이템 전부(셜커 상자·꾸러미 포함, 10장 2). 정산 때 옮기는 것은 스냅샷이 아니라 **그 순간 그 칸의 실제 스택**에서 제시 개수만큼(NBT 그대로).

## 4. 돈

- 양쪽 다 금액 제시 가능. 정수 원, 0 이상, 제시 시점 잔액 이하(`Amounts.check`). 잔액은 잡아 두지 않고 정산 때 다시 확인.
- Bank 새 API **`BankPlugin#settleTrade(extRef, a, aPays, b, bPays, source, context)`** (`source = Sources.TRADE`, 결과 `TradeOutcome`): 한 SQLite 트랜잭션(`BEGIN IMMEDIATE`) 안에서 양쪽 계좌 잠금 → 각자 `잔액 ≥ 자기 지급액` 확인 → 두 방향 이동 → 기록(스키마 v4 `trade_settlements` + `transactions` `TxType.TRADE`). `extRef = "trade:<tradeId>"` 로 멱등(같은 ref 재호출은 기존 결과 반환). **기록에 두 UUID와 양쪽 금액·출처를 같이 저장**하고, 재호출 때 요청 값과 다르면 `MISMATCH`(=UNKNOWN 취급, 봉인)(QA Medium #5). 결과 `OK / REJECTED(TradeFailure, affectedPlayer) / MISMATCH / UNKNOWN`.
- 정산 조회 API **`BankPlugin#findTradeByExtRef(extRef)`** (결과 `TradeLookup`: `FOUND(TradeRecord) / NOT_FOUND / ERROR`, `TradeRecord#matches(a, aPays, b, bPays)`로 일치 검증).
- **Bank 스키마 v4(`trade_settlements`, 원장 `TRADE` 행)는 v3 이전 Bank JAR 이 `/bank log` 에서 읽지 못한다**(QA ④-1 재현). 운영은 Bank 첫 배포가 v4라 해당 없음. 이후 Bank 를 v3 이하로 되돌려야 하면 JAR 만 되돌리는 `rollback.sh` 로는 안 되고 **같은 시점 전체 스냅샷 복원**(ECONOMY.md 2.3)으로만.
- 받는 쪽 최종 잔액이 `Amounts.MAX`(2^53−1)를 넘으면 `REJECTED(BALANCE_LIMIT)`(같은 트랜잭션 안에서 확인).
- 수수료·한도 없음(10장 3). 정산 때 잔액 부족이면 **거래 취소**(7.3 "잔액 부족 시 거래 취소", v1의 OPEN 복귀를 바꿈).

## 5. 정산

저널 `plugins/Trade/journal/<tradeId>.bin`(임시 파일 → fsync → 원자적 이동, `AtomicFiles`)이 거래의 진행 상태와 **맡긴 아이템 보관소**다.

| 단계 | 하는 일 (메인 스레드) | 실패하면 |
| --- | --- | --- |
| 1 재검증 | 둘 다 온라인·같은 `(tradeId, gen)`·서바이벌/모험·전투 아님·대화창 닫힘, 제시가 3장 조건 충족, 양쪽 잔액 ≥ 자기 지급액·받는 쪽 최종 잔액 ≤ `Amounts.MAX` | 준비 해제 + 이유 안내(잔액 부족은 취소) |
| 2 의도 기록 `TAKING` | 양쪽 제시를 **그 순간 그 칸의 실제 스택에서 직렬화**(`ItemStack#serializeAsBytes`)해 저널에 기록, fsync | 쓰기 실패 → 아무것도 안 바뀜, 준비 해제 + severe |
| 3 가져오기 (양쪽 같은 틱) | 각자 제시 칸에서 제시 개수 제거 + PDC `trade:applied`에 `<tradeId>:take:<uuid>` → `saveData()` → 디스크 확인 | `FOUND` 아닌 쪽: **빼낸 아이템을 돌려주지 않는다**(Market `/판매` 14.3 5번과 같음). 그 쪽 `take=PENDING`, 1분 타이머가 다시 `saveData`·디스크 확인(아래 6장) |
| 4 돈·확정 `COMMITTED` | 양쪽 `take=FOUND` 일 때만. 금액이 있으면 `settleTrade`(4장): `OK` → 저널 `COMMITTED`. `REJECTED` → 취소(7번). `UNKNOWN/MISMATCH` → 저널 유지 + 두 사람 거래 잠금, 타이머가 `findByExtRef`(있음 → COMMITTED, 없음 → 취소, 계속 모름 → 관리자). 금액이 둘 다 0원이면 바로 `COMMITTED` | — |
| 5 지급 (양쪽, 시도 번호 `n`) | 받을 물건 **전부**가 빈칸에 들어가면 지급 + PDC `trade:applied`에 `<tradeId>:give:<uuid>:<n>` → `saveData()` → 디스크 확인 | `FOUND` 아님 → **같은 틱에 지급한 물건과 토큰을 회수**(Market 13.6) 하고 `give=PENDING`. 빈칸이 모자라면 지급하지 않고 `give=PENDING` + `/trade claim` 안내 |
| 6 완료 | 양쪽 `give=FOUND` → 저널 삭제, 거래 로그, 안내 | — |
| 7 취소(확정 전) | 확정 전에 끝난 경우(`REJECTED`, 금액 있는 거래는 `findByExtRef` 로 **미정산 확인 후**, 확정 ABSENT 로 판명된 가져오기 등): **첫 반환 전에 저널을 `RETURNING` 으로 fsync**(단방향 — 이 상태에서는 다시 정산하지 않음, v4 재검증 Critical). 그 뒤 `take=FOUND` 인 쪽에 **자기 물건을 5번과 같은 방식으로 돌려줌**. `take` 가 확정 `ABSENT` 인 쪽은 디스크에 원래 물건이 그대로이므로 할 일 없음 | 돌려주기도 5번과 같은 실패 처리(`/trade claim`) |

- **토큰 이름은 목적·받는 사람·시도로 구분**: `<tradeId>:take:<uuid>`, `<tradeId>:give:<uuid>:<n>`, `<tradeId>:return:<uuid>:<n>`. 쓰는 곳·읽는 곳 모두 이 한 규격(`TradeTokens` 클래스 하나)만 쓴다. **판정 규칙**: 같은 목적·받는 사람의 토큰이 디스크에 **어느 시도 번호로든** FOUND 면 그 목적은 이미 반영된 것이므로 다시 지급하지 않는다. 회수는 같은 틱 안에서 토큰까지 같이 지우므로, 디스크에 남은 토큰은 실제로 반영된 시도만 가리킨다(Market 시도 번호와 같은 근거).
- `give/return PENDING` 은 그 플레이어가 접속해 있을 때 1분 타이머, 접속할 때, `/trade claim` 때 새 시도 번호로 5번을 다시 한다(한 번에 전부, 부분 지급 없음 — 배치 토큰 문제 없음).
- 가져오기가 `PENDING` 인 동안 그 플레이어의 메모리 인벤토리에는 이미 물건이 없다(돌려주지 않았으므로). 디스크에 남은 쪽이 맞는지는 6장이 정한다.

## 6. 복구 (기동·접속·1분 타이머)

| 저널 상태·쪽 상태 | 디스크 확인 | 처리 |
| --- | --- | --- |
| `TAKING`, 쪽 `take=PENDING` (서버 실행 중, **가져오기를 한 그 접속 세션이 계속되는 동안만** — 플레이어마다 접속할 때 새 `connGen`) | 타이머가 `saveData` 후 확인 | `FOUND` → `take=FOUND`. `ABSENT`(파일을 읽었는데 토큰 없음) → 메모리와 디스크가 다름 = 저장이 안 되고 있음 → 다시 저장 시도, 3회 연속이면 그 플레이어 Trade 잠금 + severe(관리자). `UNREADABLE` → 기다림 |
| `TAKING`, 그 플레이어가 **퇴장했거나 다시 접속함**(connGen 이 바뀜) | 퇴장 저장 뒤 / 재접속 때 그 플레이어의 디스크 `.dat` | **그 플레이어 쪽만** 메모리 상태를 버리고 디스크로 판정(FOUND / 확정 ABSENT / UNREADABLE). 상대 쪽은 상대의 상태대로 따로 판정한다 |
| `TAKING` (기동 때, 모두 오프라인) | 각 쪽 `.dat` | `FOUND` → 가져오기 됨. `ABSENT` → 가져오기 안 됨(디스크에 원래 물건). `UNREADABLE` → 기다림(잠금) |
| `TAKING`, 결정 | 양쪽 take 의 **최종** 상태 | 양쪽 FOUND → 4번부터 계속. 한쪽이라도 확정 ABSENT **이고 다른 쪽이 PENDING(같은 접속에서 저장 중)·UNREADABLE 이 아니면** → 7번 취소. 그 밖(어느 쪽이든 아직 PENDING·UNREADABLE) → **결정 유예**(다른 쪽이 FOUND/ABSENT 로 끝날 때까지 기다림, v4.1 재검증 Critical) |
| `RETURNING` | 쪽별 `return` 토큰 | 정산은 절대 다시 하지 않음. 돌려받지 못한 쪽만 5번 방식으로 돌려줌 |
| `COMMITTED`, `give=PENDING` | 접속·타이머·`/trade claim` 때 5번 | 위 5번 그대로 |
| 금액 있는 `TAKING`→`COMMITTED` 사이에서 멈춤 | `findByExtRef` | 있음·일치 → `COMMITTED`, 없음 → 4번 다시(양쪽 take FOUND 면 정산 재시도) 또는 7번, 모름 → 잠금 |

- 정산 중이거나 대기(`PENDING`)가 남은 플레이어는 Trade 새 거래 불가(다른 기능은 막지 않음).
- **저널 손상**(읽기·역직렬화 실패): **먼저 `journal/LOCKED` 표시 파일을 fsync 로 만든 뒤** 손상 파일을 `journal/corrupt/` 로 옮긴다(v4 재검증 High — 순서가 반대면 그 사이 종료 때 잠금이 사라짐). **`LOCKED` 가 있거나 `journal/corrupt/` 에 해결 표시 없는 파일이 있으면 기동·reload 때도 Trade 전체 잠금**(누가 관련됐는지 모르므로). 관리자가 파일을 확인하고 `/trade resolve unlock` 을 실행하면: 격리 파일마다 **해결 표시(`<파일>.resolved`, 관리자·시각·조치)를 fsync 로 먼저 남기고**, 해결 표시가 없는 격리 파일이 하나도 없을 때만 `LOCKED` 를 지운다.
- 남는 위험(문서로 인정, v4 재검증): ① 디스크가 계속 저장에 실패하거나 `.dat` 을 못 읽는 상태는 잠금 + 관리자 개입으로만 막는다. ② 서버 밖에서 `.dat` 하나만 예전 백업으로 되돌리는 경우는 Trade 가 감지하지 못한다 → **복원은 ECONOMY.md 2.3대로 서버 정지 상태의 같은 시점 전체 백업으로만**(경제 데이터·플레이어 파일·Trade 저널을 같이) 한다. Market `PlayerDataGuard` 의 `seq` 대조를 Trade 에도 쓸지는 구현 단계에서 판단(공통으로 옮길 수 있으면 `common`).

## 7. 클릭·이벤트

- 거래 창은 모든 클릭·드래그(`InventoryClickEvent` 전부 — 창 바깥 클릭 `OUTSIDE`, `InventoryCreativeEvent` 포함)를 취소한 뒤 해석만 한다. 창을 열 때 플레이어 커서에 아이템이 있으면 **창을 열지 않고** "손에 든 아이템을 먼저 내려놓아 주세요" 안내(커서를 대신 옮기지 않음): 아래 인벤토리 좌·우클릭(제시 추가), 위 제시 칸 좌·우클릭(빼기), `4` 금액, `40` 준비 토글, `49` 취소. Shift·숫자키·`F`·`Q`(창 안 버리기)·더블클릭·드래그·크리에이티브 중클릭·꾸러미 우클릭(내용 넣고 빼기)은 **아무 동작 없음**(QA Medium #6). 커서에 아이템이 올라갈 일이 없으므로 "창 밖 커서 버리기"도 생기지 않음.
- 금액 대화창(Paper Dialog): 열 때 `(tradeId, gen)` 과 함께 **일회성 콜백** 등록, 본인 준비 자동 해제 + 정산 불가, 60초 만료(제안). 응답 때 세대가 다르거나 세션이 끝났으면 무시. 대화창이 떠 있는 동안 거래 창은 닫힌 상태지만 **그 대화창을 여느라 닫힌 한 번만** 취소로 보지 않음(10장 1) — 대화창 종료(확인·취소·ESC·만료) 때 거래 창을 다시 연다. 대화창 중 로그아웃·사망은 그대로 취소.
- 이벤트: `PlayerQuitEvent`·`PlayerKickEvent`(MONITOR), `PlayerDeathEvent`(MONITOR, keepInventory 와 무관하게 취소 — 아이템이 안 움직이므로 반환 불필요), `InventoryCloseEvent`(대화창 전환 표시가 없으면 취소), `PlayerGameModeChangeEvent`, 전투(`EntityDamageByEntityEvent` MONITOR 뒤 다음 틱에 Travel PDC 재확인). Paper 26.3-258 에서 Dialog 를 열 때 `InventoryCloseEvent` 가 어떤 순서로 오는지 구현 때 확인해 주석으로 남긴다.
- 요청 타임아웃 30초, 카운트다운 3초(7.3), `ClickLock` 250ms.

## 8. 받을 물건 대기(`/trade claim`)

- 5번 지급·7번 돌려주기가 빈칸 부족·디스크 확인 실패로 끝나면 그 쪽은 `PENDING`. 물건은 저널이 보관한다(월드에 떨어뜨리지 않음).
- `/trade claim`: 받을 물건 전부가 빈칸에 들어갈 때만 한 번에 지급(5번). 안 들어가면 "빈칸 n칸이 필요합니다" 안내. Market `/market claim` 과 같은 방식.
