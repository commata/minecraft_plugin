# `/trade` 1:1 교환 — 로직 설계 (Trade 플러그인)

> 상태: **로직 설계 확정 v2** (2026-11-27). v1(4e70587)은 설계 QA(codex `gpt-6.2-sol` high)에서 Critical 2·High 2·Medium 3이 나와 **"제시 방식 + 정산 앞으로 진행(roll-forward)"** 으로 다시 설계함(사용자 결정 2026-11-27, 11장). 규칙·레이아웃 원본은 [ECONOMY.md 7.3·7.4.6](ECONOMY.md).
> 단계: ① 로직 설계(이 문서) → ② GUI 설계(7.4.6) → ③ 구현(DEV) → ④ QA(Level 4) → ⑤ 피드백 수정 → 테스트 서버 검증 → 운영 첫 배포에 포함(STATUS.md 7장).

## 0. 핵심 원칙

1. **아이템은 정산 순간까지 각자 인벤토리에서 움직이지 않는다.** 거래 창의 "내 제시 칸"은 내 인벤토리 칸을 가리키는 **표시**일 뿐이다(제시 방식). 그래서 취소·로그아웃·사망·강제 종료에 **돌려줄 것이 없다**(반환·발밑 드롭·반환 보관함 없음).
2. **정산은 "확정 기록(커밋 지점)" 뒤에는 앞으로만 진행한다.** 확정 기록 전에 끊기면 아무 일도 없던 것, 뒤에 끊기면 반영 안 된 쪽을 나중에 마저 반영한다. 되돌리기(rollback)는 없다.
3. 각 플레이어 쪽 반영은 그 플레이어의 `.dat` 한 파일 안에서 **"인벤토리 변경 + 적용 토큰"이 같이** 저장되므로, 토큰이 있으면 반영됨·없으면 반영 안 됨으로 판정한다(Market 13.6과 같은 근거, AGENTS.md 5.4).

## 1. 범위

- 새 플러그인 `plugins/trade`, `plugin.yml` 이름 **`Trade`**, 패키지 `kr.commata.trade`.
- 의존: `depend: [Vault]`, `softdepend: [Bank, Travel, EconomyHub]`. Bank가 없거나 잠기면 **거래 기능 전체 잠금**(10장 5).
- 명령: `/trade` (`/거래`) 접속자 선택 창, `/trade <닉네임>` 요청, `/trade accept|deny [닉네임]`, `/trade claim`(정산 뒤 인벤토리가 모자라 남은 받을 물건 수령, 8장), `/trade status`·`/trade reload`·`/trade resolve <tradeId>`(관리자). 권한 `trade.use`(기본 모두), `trade.admin`(op).
- **크리에이티브·관전 모드에서는 요청·수락·정산 불가**(크리에이티브 아이템이 서바이벌 경제로 들어오는 것 방지, ECONOMY.md 8장 "크리에이티브 보상"과 같은 원칙).

## 2. 세션 상태와 세대

```
 (없음) ─/trade B─▶ REQUESTED ─30초·거절·한쪽 종료─▶ (없음)        재요청 금지 10초(10장 4)
                       │ 수락
                       ▼
                     OPEN ◀──────────── 변경·준비 해제·대화창 열림 ───┐
                       │ 양쪽 준비                                     │
                       ▼                                               │
                   COUNTDOWN (3초) ─────────────────────────────────────┘
                       │ 0초
                       ▼
                   SETTLING ──REJECTED(잔액 부족 등)──▶ CANCELLED
                       │ 커밋 지점(5장 3)
                       ▼
                   COMMITTED ──양쪽 반영 확인──▶ COMPLETED
```

- 한 플레이어는 세션 하나(보낸 요청·받은 요청 포함). **정산 기록(저널)이 남은 플레이어**는 새 요청·수락 불가.
- 세션은 `tradeId`(UUID)와 **세대 번호 `gen`** 을 가진다. 아이템·금액·준비 상태가 바뀔 때마다 `gen += 1`, 양쪽 준비 해제, 카운트다운 취소. 대화창 응답·카운트다운 틱·지연 작업은 시작할 때의 `(tradeId, gen)`을 들고 있다가 **다르면 무시**(QA High #4).
- 종료 사유(사망, 로그아웃·강퇴·화이트리스트 제거로 인한 퇴장, 창 닫기, 취소 버튼, 전투 태그, 모드 변경, 플러그인 종료)는 **이벤트 안에서 즉시** 세션을 CANCELLED로 바꾼다(창 닫기 같은 화면 처리만 다음 틱). OPEN/COUNTDOWN 에서는 아이템이 안 움직였으므로 그걸로 끝. SETTLING 이후에는 취소하지 않고 5장대로 진행.
- 서버 재시작: REQUESTED·OPEN·COUNTDOWN 은 메모리에만 있으므로 그냥 사라진다(아이템 영향 없음). SETTLING·COMMITTED 는 저널로 복구(6장).
- 전투: 요청·수락·준비·정산 직전에 Travel PDC `home:combat_until` 확인(키 이름 고정, AGENTS.md 2.4). Travel 이 없으면 검사 생략 + `/trade status` 표시. 차원 이동·텔레포트는 취소 사유가 아님(7.3 거리 제한 없음, 아이템이 안 움직이므로 위험 없음).

## 3. 제시 (아이템)

- 제시 = `(내 인벤토리 칸 번호, 그 칸 아이템의 스냅샷, 제시 개수)`. 한 칸은 한 번만, 최대 16칸(7.4.6 4×4).
- 조작(② GUI 설계에서 확정): 아래 내 인벤토리 칸 좌클릭 = 그 칸 전부 제시, 우클릭 = 1개 추가. 위 "내 제시 칸" 좌클릭 = 빼기, 우클릭 = 1개 빼기. **아이템은 실제로 움직이지 않음** — 거래 창은 `common.gui` 처럼 모든 클릭을 취소하고 위 동작만 해석한다(v1의 "본인 칸 넣고 빼기 예외"는 없어짐).
- 창이 열려 있는 동안 플레이어는 인벤토리를 직접 조작할 수 없지만, 땅의 아이템 줍기·다른 플러그인 지급으로 칸 내용이 바뀔 수 있다. 그래서 **매 틱·정산 직전에 "그 칸에 같은 아이템(isSimilar)이 제시 개수 이상 있는지"** 를 다시 확인하고, 달라졌으면 그 제시를 지우고 `gen += 1`(준비 해제) + 안내.
- 거래 가능: 바닐라 아이템 전부(셜커 상자·꾸러미 포함, 10장 2). 정산 때 옮기는 것은 스냅샷이 아니라 **그 순간 그 칸의 실제 스택**에서 제시 개수만큼(NBT 그대로).

## 4. 돈

- 양쪽 다 금액 제시 가능. 정수 원, 0 이상, 제시 시점 잔액 이하(`Amounts.check`). 잔액은 잡아 두지 않고 정산 때 다시 확인.
- Bank 새 API **`settleTrade(extRef, a, aPays, b, bPays, context)`**: 한 SQLite 트랜잭션 안에서 양쪽 계좌 잠금 → 각자 `잔액 ≥ 자기 지급액` 확인 → 두 방향 이동 → 기록. `extRef = "trade:<tradeId>"` 로 멱등(같은 ref 재호출은 기존 결과 반환). **기록에 두 UUID와 양쪽 금액을 같이 저장**하고, 재호출·`findByExtRef` 때 요청 값과 다르면 `MISMATCH`(=UNKNOWN 취급, 봉인)(QA Medium #5). 결과 `OK / REJECTED(사유) / UNKNOWN`.
- 수수료·한도 없음(10장 3). 정산 때 잔액 부족이면 **거래 취소**(7.3 "잔액 부족 시 거래 취소", v1의 OPEN 복귀를 바꿈).

## 5. 정산 (메인 스레드, 한 틱)

1. **재검증**: 둘 다 온라인·같은 `(tradeId, gen)`·서바이벌/모험·전투 아님·대화창 닫힘, 모든 제시가 3장 조건 충족, 양쪽 잔액 ≥ 자기 지급액, **받을 아이템이 들어갈 자리**(자기 제시분을 뺀 뒤의 인벤토리에 스택 합치기 포함 시뮬레이션). 실패 → 준비 해제 + 이유 안내(잔액 부족만 취소).
2. **저널 기록 `SETTLING`** `plugins/Trade/journal/<tradeId>.bin` (임시 파일 → fsync → 원자적 이동, `AtomicFiles`): tradeId, 두 UUID·닉, 양쪽 제시(칸 번호·개수·**그 순간 실제 스택 직렬화** `ItemStack#serializeAsBytes`), 양쪽 금액, extRef. 쓰기 실패 → 아무것도 안 바뀐 상태로 준비 해제 + severe 로그.
3. **커밋 지점**
   - 금액이 있으면 `settleTrade`: `OK` → 저널 `COMMITTED`(fsync). `REJECTED` → 저널 삭제 + 거래 취소. `UNKNOWN/MISMATCH` → 저널 `SETTLING` 유지 + 두 플레이어 거래 잠금, 1분 타이머가 `findByExtRef` 로 다시 확인(있음 → COMMITTED, 없음 → 저널 삭제·취소, 계속 모름 → 관리자 `/trade resolve`). **아이템은 아직 안 움직였으므로 어느 경우도 안전.**
   - 금액이 둘 다 0원이면 Bank 를 부르지 않고 **저널을 처음부터 `COMMITTED` 로 기록**한다(2번과 같은 쓰기). 0원 거래의 커밋 지점 = 이 저널(QA Critical #2).
4. **반영 (양쪽 각각)**: 그 플레이어의 제시 칸에서 제시 개수 제거 → 받을 아이템 추가 → PDC `trade:applied`(최근 tradeId 목록, Market `AppliedTxTokens` 와 같은 형식)에 tradeId 추가 → `saveData()` → `.dat` 에서 토큰 확인(`PlayerDatReader`). 확인된 쪽은 저널에 `appliedA/B=true` 기록.
5. 양쪽 다 확인 → 저널 삭제, 거래 로그 기록, 양쪽 안내. 한쪽이라도 확인 못 하면(`ABSENT/UNREADABLE`) 저널 `COMMITTED` 유지 → 6장 복구.

## 6. 복구 (기동·접속·1분 타이머)

| 저널 상태 | 판단 | 처리 |
| --- | --- | --- |
| `SETTLING` (금액 있음) | `findByExtRef` | 없음 → 저널 삭제(아무 일 없음). 있음·값 일치 → `COMMITTED` 로 올리고 아래. 모름·불일치 → 봉인(관리자) |
| `SETTLING` (0원) | 저널을 COMMITTED 로 쓰기 전에 멈춘 것 | 저널 삭제(아무 일 없음) |
| `COMMITTED` | 각 플레이어 `appliedX` | 그 플레이어가 접속해 있으면(또는 다음 접속 `PlayerJoinEvent` LOWEST, 다른 처리보다 먼저) **살아 있는 PDC 의 `trade:applied` 토큰**을 본다: 있음 → 반영됨으로 표시. 없음 → **지금 반영**: 저널의 제시 칸에 같은 아이템이 제시 개수 이상 있는지 확인 → 있으면 4장 4번 그대로 수행(받을 물건이 안 들어가면 남은 것은 저널의 `claim` 으로, 8장). 제시 아이템이 없으면(서버 밖에서 파일이 바뀐 경우 등) 그 쪽을 **봉인**하고 관리자 확인 |

- 접속 시점의 인벤토리는 디스크 `.dat` 에서 읽힌 것이므로, 토큰 유무가 곧 그 `.dat` 가 거래 전 상태인지 후 상태인지를 말해 준다. 그래서 "예전 .dat 가 새 .dat 를 덮음"(QA High #3) 상황에서도 토큰 기준으로 다시 판단하면 일관된다.
- 반영이 남은 플레이어는 Trade 거래 불가(2장). 다른 플러그인 기능은 막지 않음.

## 7. 클릭·이벤트

- 거래 창은 모든 클릭·드래그를 취소한 뒤 해석만 한다: 아래 인벤토리 좌·우클릭(제시 추가), 위 제시 칸 좌·우클릭(빼기), `4` 금액, `40` 준비 토글, `49` 취소. Shift·숫자키·`F`·`Q`(창 안 버리기)·더블클릭·드래그·크리에이티브 중클릭·꾸러미 우클릭(내용 넣고 빼기)은 **아무 동작 없음**(QA Medium #6). 커서에 아이템이 올라갈 일이 없으므로 "창 밖 커서 버리기"도 생기지 않음.
- 금액 대화창(Paper Dialog): 열 때 `(tradeId, gen)` 과 함께 **일회성 콜백** 등록, 본인 준비 자동 해제 + 정산 불가, 60초 만료(제안). 응답 때 세대가 다르거나 세션이 끝났으면 무시. 대화창이 떠 있는 동안 거래 창은 닫힌 상태지만 **취소로 보지 않음**(10장 1) — 대화창 종료(확인·취소·ESC·만료) 때 거래 창을 다시 연다. 대화창 중 로그아웃·사망은 그대로 취소.
- 이벤트: `PlayerQuitEvent`·`PlayerKickEvent`(MONITOR), `PlayerDeathEvent`(MONITOR, keepInventory 와 무관하게 취소 — 아이템이 안 움직이므로 반환 불필요), `InventoryCloseEvent`(대화창 전환 표시가 없으면 취소), `PlayerGameModeChangeEvent`, 전투(`EntityDamageByEntityEvent` MONITOR 뒤 다음 틱에 Travel PDC 재확인). Paper 26.3-258 에서 Dialog 를 열 때 `InventoryCloseEvent` 가 어떤 순서로 오는지 구현 때 확인해 주석으로 남긴다.
- 요청 타임아웃 30초, 카운트다운 3초(7.3), `ClickLock` 250ms.

## 8. 받을 물건 보관(claim)

- 정산 때는 받을 자리를 확인하므로 보통 생기지 않는다. 6장 복구(접속 시 인벤토리가 거래 순간과 다를 때)에서만 생길 수 있음. 남은 물건은 저널의 `claim` 목록에 두고 `/trade claim` 으로 받는다(빈칸만큼). 모두 받으면 저널 삭제. 발밑 드롭은 하지 않는다.

## 9. 기록

- 돈: Bank 원장(`source=Trade`, `extRef=trade:<id>`, 두 UUID·양쪽 금액).
- 거래 로그: `plugins/Trade/trades-YYYY-MM-DD.log` 한 줄 JSON(시각, tradeId, 두 UUID·닉, 양쪽 아이템 요약·금액, 결과·복구 여부)(10장 7).

## 10. 결정 사항 (2026-11-27 사용자 확정)

1. 금액 입력: **Paper Dialog API**.
2. 거래 가능 아이템: **바닐라 아이템 전부**(셜커 상자·꾸러미 포함).
3. 수수료·한도: **없음**.
4. 같은 상대에게 거절·만료 뒤 **10초 재요청 금지**.
5. Bank 가 없거나 잠기면 **거래 기능 전체 잠금**.
6. (v1 "오프라인 반환·발밑 드롭"은 제시 방식으로 필요 없어짐)
7. 거래 로그는 **하루 단위 파일**.
8. **제시 방식**: 아이템은 정산 순간까지 인벤토리에 그대로(11장).

## 11. v1 → v2 변경 이유 (설계 QA 4e70587, codex gpt-6.2-sol high)

| QA | v1 문제 | v2 해결 |
| --- | --- | --- |
| Critical #1 | 거래 칸으로 옮긴 아이템이 저널과 플레이어 파일 중 한쪽만 저장되면 복사/유실 | 정산 전에는 아이템을 안 옮김(0장 1) |
| Critical #2 | 0원 거래는 원장이 없어 지급·반환이 같이 성립 가능 | 0원은 저널 `COMMITTED` 가 커밋 지점, 그 뒤 앞으로만(5장 3) |
| High #3 | 수령자별 토큰·덮어쓰기·반환 저장·발밑 드롭 복구 불가 | 반환 자체가 없음, 쪽별 토큰 + 접속 시 살아 있는 PDC 로 판단(6장) |
| High #4 | 종료 이벤트·대화창·지연 작업 경합 | 세대 번호, 이벤트 안 즉시 상태 전이, 일회성 대화창 콜백(2·7장) |
